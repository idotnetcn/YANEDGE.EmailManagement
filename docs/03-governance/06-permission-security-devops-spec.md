# 1. 文档目标

本文档用于明确邮件管理系统在“账号、邮件、附件、审批、协同、开放接口”场景下的安全设计与权限模型，重点说明：

1. 系统面临的主要安全风险与防护策略
2. 内部用户认证、外部应用认证、Webhook 验签机制
3. 功能权限、数据权限、领域操作权限的分层模型
4. 邮箱、线程、邮件、附件、审批等关键对象的权限规则
5. 凭据、令牌、附件、正文、日志等敏感数据的保护方案
6. 审计、告警、限流、防重、脱敏与合规控制建议

本文档是以下工作的直接依据：

- 权限点定义与 ABP 权限实现

- 数据权限过滤实现
- 安全测试与渗透测试
- 审计日志落地
- 运维安全策略与应急处置

# 3. 安全设计原则

## 3.1 最小权限原则

任何用户、角色、组织、外部应用都只应获得完成其职责所需的最小权限，包括：

- 最小功能权限
- 最小数据可见范围
- 最小敏感操作权限
- 最小开放接口 scope

## 3.2 默认拒绝原则

对于未明确授权的功能、数据和资源访问，系统应默认拒绝，而不是默认放行。

## 3.3 分层防护原则

系统安全不依赖单点控制，而采用多层防护：

- 网络层
- 接口层
- 应用层
- 领域层
- 数据层
- 日志审计层

## 3.4 认证与授权分离原则

- 认证负责“你是谁”
- 授权负责“你能做什么”
- 数据权限负责“你能看到哪些数据”
- 领域约束负责“你在当前状态下是否允许执行该动作”

## 3.5 高风险操作强审计原则

以下操作必须具备强审计能力：

- 邮箱账号新增与修改
- 密码/令牌变更
- 敏感附件下载
- 审批通过/拒绝
- 发件执行
- 规则修改
- 模板发布
- Open API 写操作
- Webhook 配置变更

## 3.6 明文最少原则

密码、密钥、令牌、敏感附件访问令牌、签名密钥等不允许明文持久化或明文记录日志。

## 3.7 安全优先于便利原则

在邮件这类高敏感、高对外通信系统中，错误的放权、绕过审批、错误下载附件，往往比“多一步确认”危害更大。

# 4. 威胁模型与风险总览

## 4.1 主要资产识别

邮件管理系统中的核心安全资产包括：

1. 邮箱账号凭据
2. 邮件正文与历史通信记录
3. 附件文件
4. 外发能力
5. 审批结果
6. 外部应用密钥
7. Webhook 签名密钥
8. 审计日志
9. 用户身份与组织授权关系

## 4.2 主要威胁场景

| 威胁类型 | 场景说明 |
|---|---|
| 凭据泄露 | 邮箱密码、AccessToken、RefreshToken 泄露 |
| 越权访问 | 用户访问无权限邮箱/线程/附件 |
| 伪造发送 | 非授权用户使用系统邮箱发件 |
| 审批绕过 | 未审批直接发送敏感邮件 |
| 重放攻击 | Open API 请求被重复提交 |
| Webhook 伪造 | 外部伪造成功回执或内部投递被伪造 |
| XSS | 恶意 HTML 邮件正文在前端执行脚本 |
| 恶意附件 | 木马、病毒、钓鱼文件通过附件传播 |
| 数据泄露 | SQL 查询越权、对象存储地址泄露 |
| 日志泄露 | 日志中包含密钥、正文、附件临时签名 |
| 批量撞库/枚举 | 登录、Open API、下载接口被暴力尝试 |
| SSRF/回调风险 | Webhook 指向恶意内网地址 |
| 供应链风险 | 第三方库、邮件解析组件漏洞 |
| 内部滥用 | 管理员或高权限人员下载敏感附件、批量导出数据 |

## 4.3 风险分级建议

| 风险级别 | 示例 |
|---|---|
| 极高 | 邮箱凭据泄露、审批绕过、任意发件、敏感附件越权下载 |
| 高 | 邮件正文越权查看、Open API 重放、Webhook 伪造 |
| 中 | 日志脱敏不足、规则误配置、下载频率未限制 |
| 低 | 非敏感统计页越权、普通搜索接口限流不足 |

```text

  ↓

  ↓
```

# 6. 身份认证设计

# 6.1 内部用户认证

## 6.1.1 认证方式
内部用户采用：

- OIDC / OAuth2
- JWT Bearer Token
- ABP Identity 集成

## 6.1.2 基本要求
- 强制 HTTPS
- 支持单点登录
- 支持用户禁用后立即失效
- Token 过期时间可配置
- 高风险操作可要求二次确认或重新验证

## 6.1.3 登录安全建议
- 密码复杂度策略
- 登录失败次数限制
- 异常 IP 登录告警
- 可选 MFA（建议管理员、审批人、高权限人员启用）

---

## 6.2 会话与 Token 设计

### Access Token
- 有效期建议：30 分钟 ~ 2 小时
- 用于接口调用
- 不存储敏感权限以外的冗余业务数据

### Refresh Token
- 有效期建议：7 天 ~ 30 天
- 仅在可信登录终端使用
- 支持吊销与轮换

### 安全要求
- Token 不写入普通业务日志
- 浏览器端优先采用安全存储策略
- 服务端支持 Token 吊销校验

---

## 6.3 外部应用认证

外部应用调用 Open API 时，不使用内部用户 JWT，而采用：

- `X-App-Key`
- `X-Timestamp`
- `X-Nonce`
- `X-Signature`

并校验：

1. App 是否启用
2. Timestamp 是否在允许时间窗内
3. Nonce 是否已使用
4. Signature 是否正确
5. Scope 是否足够

# 7. 授权模型设计

## 7.1 授权分层模型

本系统授权采用四层模型：

### 第一层：功能权限
决定是否能访问某菜单、按钮、接口。

### 第二层：数据权限
决定是否能看到某邮箱、某线程、某附件、某审批数据。

### 第三层：领域操作权限
决定在当前业务状态下，是否允许执行认领、转派、归档、审批、发送等操作。

### 第四层：敏感操作增强校验
针对高风险操作增加额外条件，例如：
- 管理员权限
- 敏感附件下载权限
- 二次确认
- 审批人身份校验
- 原因说明必填

## 7.2 授权判定流程

建议统一采用以下判定顺序：

```text
1. 是否已认证
2. 是否具备功能权限
3. 是否具备数据可见权限
4. 当前业务状态是否允许该动作
5. 是否满足附加安全条件
6. 记录审计日志
```

## 7.3 授权实现落点

| 层级 | 建议实现方式 |
|---|---|
| 功能权限 | ABP Permission Definition + `[Authorize]` |
| 数据权限 | `IMailDataPermissionService` + Query Service |
| 领域操作权限 | `IMailAuthorizationService` + Domain Service |
| 高风险增强校验 | AppService / DomainService / Policy |

# 9. 数据权限设计

# 9.1 数据权限核心思想

功能权限通过后，仍需控制用户可见的数据范围。
数据权限的核心不是“有没有这个菜单”，而是“能不能看到这封邮件、这个线程、这个附件”。

## 9.2 数据权限来源

数据权限可由以下因素综合决定：

1. 邮箱账号授权
2. 所属组织范围
3. 当前负责人
4. 历史参与人
5. 审批参与人
6. 管理员全局权限
7. 业务对象关联范围

## 9.3 数据权限对象

建议对以下对象实施数据权限控制：

- `mail_account`
- `mail_thread`
- `mail_message`
- `mail_attachment`
- `mail_send_task`
- `mail_approval`
- `mail_internal_note`
- `audit logs`

## 9.4 邮箱级数据权限

用户可访问某邮箱的条件建议为：

满足以下任一项即可：
1. 具备全局管理员权限
2. 是邮箱所属用户
3. 是邮箱所属组织授权成员
4. 在 `mail_account_permission` 中被直接授权
5. 通过角色/组织获得该邮箱授权

权限维度包括：

- 可查看
- 可发件
- 可管理
- 可下载附件
- 可审批
- 可查看审计

## 9.5 线程级数据权限

用户可查看某线程，建议满足以下任一条件：

1. 对线程所属邮箱有查看权限
2. 是当前负责人
3. 曾被分派处理该线程
4. 是线程关联审批人
5. 具备团队/组织管理可见权限
6. 具备管理员全局查看权限

## 9.6 附件级数据权限

附件权限必须比线程权限更严格。
建议采用两级控制：

### 第一级：基础可见
有权查看所属线程/邮件。

### 第二级：下载授权
还需满足：
- 具备附件下载权限
- 如为敏感附件，具备 `DownloadSensitive`
- 通过附件访问策略校验
- 记录审计日志

## 9.7 审批级数据权限

审批对象建议按以下规则控制：

- 发起人可查看自己发起的审批
- 当前审批人可查看待处理审批
- 历史审批人可查看已处理审批摘要
- 主管/管理员可查看团队审批
- 普通处理员默认不可查看非关联审批

# 10. 关键业务对象权限规则

# 10.1 邮箱账号权限规则

| 操作 | 权限要求 | 数据条件 | 备注 |
|---|---|---|---|
| 查看邮箱详情 | `MailAccounts.View` | 对该邮箱有查看权限 | |
| 修改邮箱配置 | `MailAccounts.Update` | 对该邮箱有管理权限 | 高风险，强审计 |
| 测试连接 | `MailAccounts.TestConnection` | 对该邮箱有管理权限 | 不返回敏感细节 |
| 手动同步 | `MailAccounts.TriggerSync` | 对该邮箱有管理权限 | 限流 |
| 配置邮箱授权 | `ManagePermissions` | 对该邮箱有管理权限 | 高风险 |

## 10.2 邮件/线程查看规则

### 查看线程详情
要求：
- `Threads.View`
- 且具备线程数据可见权限

### 查看邮件详情
要求：
- `Messages.View`
- 且所属线程可见

### 查看邮件头
要求：
- `Messages.ViewHeaders`
- 一般限管理员或技术排障角色

## 10.3 认领规则

线程认领需同时满足：
1. 有 `Threads.Claim` 权限
2. 线程处于允许认领状态
3. 用户对所属邮箱有处理权限
4. 线程未被更高优先级锁定处理

## 10.4 分派/转派规则

线程分派需同时满足：
1. 有 `Threads.Assign` 或 `Threads.Transfer` 权限
2. 用户对线程具备可操作权
3. 目标对象在有效组织或授权范围内
4. 已归档/已关闭线程不允许分派

## 10.5 发件规则

发件前必须校验：
1. `SendTasks.Send` 权限
2. 对发件邮箱有 `can_send` 数据授权
3. 发件任务状态合法
4. 若命中审批策略，则审批通过
5. 账号健康状态允许发件
6. 幂等校验通过

## 10.6 审批规则

审批通过/拒绝必须满足：
1. 有 `Approvals.Approve` 或 `Approvals.Reject` 权限
2. 当前用户是该步骤合法审批人
3. 审批单状态为待审批
4. 审批操作具备审计记录
5. 操作不可重复提交

## 10.7 附件下载规则

附件下载必须满足：
1. `Attachments.Download` 权限
2. 用户对所属线程/邮件可见
3. 用户对所属邮箱具备下载权限
4. 若附件为敏感级别，具备 `DownloadSensitive` 或特殊授权
5. 下载动作记录日志
6. 可选启用二次确认或短期签名地址

# 11. Open API 安全设计

# 11.1 安全目标

开放平台 API 的核心风险在于：

- 伪造请求
- 重放攻击
- scope 越权
- 高并发重复提交
- 密钥泄露后滥用

因此 Open API 必须具备：

- 应用级身份认证
- 请求签名
- 时间窗校验
- Nonce 防重放
- 幂等键
- 调用频率限制
- 审计日志

## 11.2 签名机制

建议签名串：

```text
method + "\n" +
path + "\n" +
timestamp + "\n" +
nonce + "\n" +
bodyHash
```

算法：
- `HMACSHA256(appSecret, signContent)`

## 11.3 时间窗校验

- 默认允许时间偏差：`±5 分钟`
- 超出时间窗直接拒绝
- 返回 `INTEGRATION.AUTH.INVALID_TIMESTAMP`

## 11.4 Nonce 防重放

- Nonce 在有效时间窗内只能使用一次
- 建议缓存存储（Redis）
- 已使用 Nonce 再次提交则拒绝

## 11.5 Scope 控制

应用调用前必须校验 scope，例如：

| 接口 | 需要 Scope |
|---|---|
| 创建待发邮件 | `mail.send` |
| 查询线程摘要 | `mail.read` |
| 写入业务关联 | `mail.relation.write` |
| 查询审批状态 | `mail.approval.read` |

## 11.6 限流建议

按应用维度限流：

- 默认 QPS 限制
- 突发阈值限制
- 按接口分级限制
- 失败请求过高时熔断告警

## 11.7 幂等设计

对写接口强制支持 `Idempotency-Key`，防止：

- 网络抖动重复提交
- 第三方重试导致重复发件
- 中间件超时重发

---

# 12. Webhook 安全设计

# 12.1 安全风险

Webhook 面临的主要风险：

- 回调地址配置错误
- 指向恶意地址或内网地址
- 伪造投递结果
- 重放旧事件
- 响应超时导致积压

## 12.2 回调地址校验

创建 Webhook 订阅时建议校验：

- 必须为 HTTPS
- 禁止指向本地回环地址
- 禁止指向内网保留地址段（视部署策略）
- 可加入域名白名单机制

## 12.3 签名设计

Webhook 推送时在 Header 中附带：

- `X-Event-Id`
- `X-Event-Code`
- `X-Event-Time`
- `X-Signature`

签名建议基于：
- 事件 ID
- 事件时间
- 请求体 Hash
- 订阅密钥

## 12.4 投递安全

- 至少一次投递
- 每次投递记录状态
- 响应超时后自动重试
- 达到阈值后告警并暂停
- 支持手工重推

## 12.5 防重建议

外部接收方应以 `eventId` 去重。
本系统内部也要保证 `eventId + subscriptionId` 唯一。

# 13. 凭据与密钥管理

# 13.1 需保护的敏感信息

以下信息必须按密钥级别管理：

- 邮箱密码
- AccessToken
- RefreshToken
- AppSecret
- Webhook Signing Secret
- 附件临时访问令牌
- 加密主密钥引用信息

## 13.2 存储原则

- 数据库存储加密后的密文
- 不写入日志
- 不通过接口明文返回
- 配置文件中不得硬编码生产密钥
- 优先接入专用 Secret 管理服务

## 13.3 加密建议

建议使用：

- 应用层统一加密服务
- 对称加密存储敏感字段
- 密钥版本号管理
- 支持密钥轮换

## 13.4 密钥轮换策略

| 密钥类型 | 轮换建议 |
|---|---|
| Open API AppSecret | 支持人工轮换，保留短期双密钥窗口 |
| Webhook Secret | 支持重置和生效时间 |
| 应用主密钥 | 有计划轮换，支持密文重加密 |
| 附件临时下载令牌 | 短生命周期，无需长期轮换 |

## 13.5 展示规则

对于后台管理界面：

- 密钥默认不回显
- 仅支持“重置/轮换”
- 如需展示，仅展示前后缀片段
- 关键操作必须审计

# 14. 数据安全设计

# 14.1 数据分类建议

建议将数据划分为四级：

| 级别 | 示例 |
|---|---|
| L1 公共 | 系统帮助信息、非敏感配置 |
| L2 内部 | 普通业务邮件元数据、统计摘要 |
| L3 敏感 | 邮件正文、内部备注、联系人信息 |
| L4 高敏感 | 附件、审批意见、邮箱凭据、访问令牌 |

## 14.2 存储保护要求

| 数据类型 | 保护要求 |
|---|---|
| 邮箱凭据 | 强加密 |
| 邮件正文 | 访问控制 + 日志脱敏 |
| 附件对象 | 独立存储、不可匿名访问 |
| 审批意见 | 权限控制 + 审计 |
| API 调用日志 | 敏感字段脱敏 |
| Webhook 日志 | 签名密钥不入日志 |

## 14.3 查询最小化原则

接口和查询服务只返回当前页面所需字段，不应默认返回：

- 原始 HTML 全文
- 全部邮件头
- 全量审批快照
- 敏感附件真实对象路径
- 密钥字段

## 14.4 导出控制建议

如后续支持导出，必须控制：

- 仅授权角色可导出
- 导出范围受数据权限限制
- 敏感字段可脱敏
- 导出动作审计
- 大批量导出限流/审批

---

# 15. 附件与文件安全设计

# 15.1 基本原则

附件是邮件系统最高风险对象之一。
必须采用“元数据入库、文件隔离存储、访问受控、下载可追踪”的设计。

## 15.2 存储要求

- 附件文件不直接暴露对象存储原始地址
- 存储桶禁止公共读
- 对象 Key 不使用可枚举规则
- 使用服务端生成短期签名 URL 或流式代理下载

## 15.3 上传与接收扫描

无论来自用户上传还是同步接收，建议执行：

- 病毒扫描
- 文件类型识别
- 扩展名与 MIME 一致性校验
- 可执行文件拦截或高风险标记
- 预览转换隔离

## 15.4 访问控制

附件访问分为：

1. 元数据查看
2. 在线预览
3. 实际下载

三者应可分别授权。

## 15.5 敏感附件控制

建议为敏感附件支持：

- 高敏感标记
- 下载二次确认
- 水印预览（可选）
- 操作理由记录（可选）
- 更严格频率限制
- 下载后告警（可选）

## 15.6 审计要求

记录以下信息：

- 下载人
- 下载时间
- 来源 IP
- User-Agent
- 是否成功
- 附件 ID
- 所属邮件/线程
- 是否敏感附件

---

# 16. 邮件正文与前端展示安全设计

# 16.1 HTML 邮件风险

HTML 邮件可能包含：

- 恶意脚本
- 内嵌事件处理器
- 外链跟踪像素
- 恶意跳转链接
- 可疑样式注入
- 钓鱼内容

## 16.2 正文处理策略

建议保留两份正文：

1. 原始 HTML
2. 清洗后 HTML（用于展示）

## 16.3 HTML 清洗要求

清洗策略建议：

- 移除 `script`
- 移除内联事件属性，如 `onclick`
- 移除危险 URL scheme，如 `javascript:`
- 限制 iframe / object / embed
- 可选阻断外链图片自动加载
- 对链接增加安全跳转或提示

## 16.4 前端展示要求

- 使用 `sanitizedHtmlBody`
- 不直接渲染原始 HTML
- 链接新窗口打开时附带 `rel=noopener noreferrer`
- 对可疑内容给予风险标识
- 支持“显示原始邮件”但仅限授权场景

## 16.5 富文本编辑安全

发件编辑器需防止：

- 存储型 XSS
- 粘贴恶意 HTML
- 非法标签注入
- 非法外链脚本

# 17. 审计与安全日志设计

# 17.1 审计目标

审计不是可选项，而是邮件系统安全闭环的核心。
必须能够回答：

- 谁在什么时候看了什么
- 谁下载了哪个附件
- 谁修改了邮箱配置
- 谁审批了哪封外发邮件
- 哪个外部应用调用了什么接口
- 哪次 Webhook 投递失败或异常

## 17.2 审计分类

| 审计类别 | 内容 |
|---|---|
| 认证审计 | 登录、登出、失败登录 |
| 授权审计 | 权限拒绝、越权尝试 |
| 配置审计 | 邮箱配置、规则、模板、Webhook 变更 |
| 业务审计 | 发件、审批、分派、归档 |
| 访问审计 | 邮件查看、附件下载、审批查看 |
| 集成审计 | Open API 调用、Webhook 投递 |
| 安全事件审计 | 签名失败、限流、重放攻击 |

## 17.3 必审计操作清单

以下操作必须审计：

- 新增/修改/删除邮箱账号
- 轮换密钥
- 测试连接
- 手工同步
- 发件提交/发送/重试
- 审批通过/拒绝/撤回
- 线程认领/分派/转派/归档/关闭
- 模板发布
- 规则启停/测试
- 附件预览/下载
- Open API 写请求
- Webhook 配置与重推

## 17.4 日志脱敏要求

日志中不得出现：

- 明文密码
- AccessToken / RefreshToken
- AppSecret
- Webhook Signing Secret
- 完整附件签名下载地址
- 完整敏感正文（按策略）
- 完整身份证号/手机号/合同密级信息（如有）

## 17.5 审计日志防篡改建议

- 关键审计日志单独存储
- 限制修改权限
- 定期归档
- 可选接入集中日志平台
- 可选计算摘要或签名链

# 18. 传输安全设计

# 18.1 HTTPS 强制要求

所有入口必须使用 HTTPS，禁止明文 HTTP 访问敏感接口。

## 18.2 TLS 建议

- 使用现代 TLS 版本
- 禁用弱加密套件
- 配置 HSTS（按部署策略）
- 管理证书有效期与自动续期

## 18.3 内部服务通信

如采用微服务或外部扫描服务，建议：

- 服务间 TLS
- 服务身份认证
- 内网不等于可信
- 关键服务接口也需鉴权

## 18.4 邮件协议连接安全

连接 IMAP / SMTP 时：

- 优先 SSL/TLS
- 禁止弱协议
- 校验证书
- 配置连接超时与失败告警

---

# 19. 接口安全防护设计

# 19.1 输入校验

所有 API 写请求必须校验：

- 必填项
- 长度
- 格式
- 枚举值
- 引用对象存在性
- 状态机合法性
- 权限合法性

## 19.2 限流与防刷

建议对以下接口限流：

- 登录接口
- Open API 写接口
- 附件下载接口
- 手工同步接口
- 全文搜索接口
- Webhook 重推接口

## 19.3 幂等防重

以下接口必须支持幂等：

- 创建待发邮件
- 发送邮件
- 重试发送
- 外部写业务关联
- Webhook 重推记录处理

## 19.4 错误信息控制

错误响应不应泄露：

- 数据库结构
- 内部堆栈
- 邮箱凭据验证细节
- 签名算法内部实现细节
- 用户是否存在的过度信息

## 19.5 CORS 策略

- 前端来源白名单
- 禁止 `*` 任意来源用于管理端
- 仅开放必要方法与 Header
- 控制凭证透传

## 19.6 CSRF 防护

若采用 Cookie 认证场景，需要启用 CSRF 防护。
如采用纯 Bearer Token，可降低此风险，但仍需校验跨域策略。

# 20. 应用层安全控制

# 20.1 服务层统一授权

建议在应用层统一使用：

- `[Authorize(PermissionName)]`
- `IMailAuthorizationService`
- `IMailDataPermissionService`

避免控制器或页面层单独散落权限逻辑。

## 20.2 高风险操作二次校验

以下操作建议二次校验：

- 下载敏感附件
- 修改邮箱授权
- 轮换 Open API 密钥
- 发布规则/模板
- 强制重发
- 恢复已归档或已关闭线程

## 20.3 审批前置控制

对于命中审批策略的发件任务：

- 应阻断直接发送
- 必须转入待审批
- 审批通过后才能进入待发

## 20.4 后台任务安全

同步任务、发件任务、Webhook 重试任务等后台作业也必须：

- 以系统身份运行
- 记录操作来源为系统任务
- 严格控制任务输入来源
- 避免任务绕过业务校验

---

# 21. 数据库与基础设施安全建议

# 21.1 数据库访问控制

- 应用账号最小权限
- 禁止使用超级管理员账号作为业务连接
- 区分只读账号与写账号（按需）
- 数据库访问来源白名单

## 21.2 备份安全

- 备份文件加密
- 限制访问备份介质
- 定期恢复演练
- 备份同样视为敏感数据

## 21.3 对象存储安全

- 存储桶私有
- 生命周期策略
- 防止公开枚举
- 短期签名 URL
- 下载来源审计

## 21.4 运行环境安全

- 最小化容器镜像
- 定期更新补丁
- 禁止在环境变量中长期暴露明文主密钥
- 管理员访问走堡垒机或审计通道

---

# 22. 安全监控与告警设计

# 22.1 监控事件建议

应重点监控以下事件：

- 登录失败暴增
- Open API 签名失败暴增
- 同一附件异常高频下载
- 同一应用高频幂等冲突
- 邮箱连接持续失败
- Webhook 投递大面积失败
- 审批绕过类异常
- 短时间大量发件
- 高频越权访问尝试

## 22.2 告警级别建议

| 级别 | 场景 |
|---|---|
| P1 | 密钥泄露疑似、异常大量发件、审批绕过、敏感附件批量下载 |
| P2 | Open API 重放攻击、Webhook 大面积失败、邮箱连接异常 |
| P3 | 单接口限流触发、普通权限拒绝激增 |

## 22.3 安全看板建议

建议建设基础安全看板，指标包括：

- 登录成功/失败趋势
- 附件下载次数与敏感附件下载排行
- Open API 调用量与失败率
- Webhook 成功率
- 审批通过/拒绝趋势
- 权限拒绝次数
- 可疑 IP 统计

---

# 23. 合规与数据生命周期建议

# 23.1 最低必要保留

系统应只保留业务所需的数据，不做无限制长期保存。

## 23.2 数据保留建议

| 数据类型 | 建议保留周期 |
|---|---|
| 核心邮件与线程 | 按业务制度 |
| 附件访问日志 | 365 天或以上 |
| Open API 调用日志 | 180 天 |
| Webhook 投递日志 | 180 天 |
| 同步日志 | 180 天 |
| 安全告警记录 | 180~365 天 |
| 审计日志 | 按合规要求长期保留 |

## 23.3 删除与归档原则

- 业务删除优先软删除
- 审计日志原则上不可被普通业务删除
- 归档数据仍需保持访问控制
- 冷归档数据需记录索引信息

## 23.4 隐私与个人信息建议

若邮件中包含个人信息，应至少做到：

- 访问控制
- 日志脱敏
- 导出限制
- 审计留痕
- 最小暴露字段

# 24. 安全测试与验收建议

# 24.1 安全测试类型

建议至少覆盖：

- 权限测试
- 越权测试
- 接口签名测试
- 幂等与重放测试
- XSS 测试
- 恶意附件测试
- 限流测试
- 日志脱敏测试
- 审计完整性测试

## 24.2 重点测试清单

### 权限类
- 无权限用户访问授权邮箱
- 通过 ID 猜测访问他人线程
- 无权限下载附件
- 非审批人审批通过

### Open API 类
- 签名错误
- 时间戳过期
- Nonce 重复
- Scope 不足
- Idempotency-Key 重放

### 邮件正文类
- HTML 脚本注入
- 恶意链接
- 外链图片追踪

### 附件类
- 双扩展名恶意文件
- MIME 伪装
- 病毒样本识别
- 越权下载

### 审计类
- 敏感操作是否记录
- 日志是否脱敏
- traceId 是否贯通

## 24.3 验收标准建议

至少满足以下标准：

1. 核心对象无明显越权漏洞
2. 敏感凭据不明文存储或日志输出
3. Open API 签名、防重放、幂等有效
4. 敏感附件下载全量留痕
5. HTML 邮件展示无明显 XSS 风险
6. 审批无法被绕过
7. 审计日志可定位关键操作责任人

# 25. ABP 与 .NET 实施建议

# 25.1 ABP 权限定义建议

在 `PermissionDefinitionProvider` 中按模块定义权限树，例如：

```text
MailManagement
 ├─ MailAccounts
 ├─ Messages
 ├─ Threads
 ├─ SendTasks
 ├─ Approvals
 ├─ Attachments
 ├─ Templates
 ├─ Rules
 ├─ BusinessRelations
 ├─ Integration
 ├─ Statistics
 └─ AuditSecurity
```

## 25.2 授权服务接口建议

建议定义：

- `IMailAuthorizationService`
- `IMailDataPermissionService`
- `IOpenApiSignatureValidator`
- `IAttachmentAccessPolicyService`
- `ISensitiveOperationGuard`

## 25.3 应用服务实现建议

在 AppService 中：

1. 先做功能权限校验
2. 再做数据权限校验
3. 再加载领域对象
4. 最后执行领域动作

避免先查出敏感实体再失败，减少信息泄露面。

## 25.4 EF Core 查询过滤建议

对高频查询读模型，建议通过：

- Query Service
- Specification
- 自定义仓储方法
- 显式 Where 条件拼接

实现数据权限，而不要完全依赖全局过滤器覆盖所有复杂场景。

## 25.5 审计集成建议

- 复用 ABP 审计模块记录通用请求审计
- 对敏感业务行为使用独立审计表
- 对附件下载、审批、Open API 调用进行专项日志记录

## 25.6 加密实现建议

建议封装统一接口：

- `ISecretEncryptionService`
- `ITokenProtectionService`

避免每个模块自行处理加密逻辑。

# 26. 结论

邮件管理系统的安全设计应围绕以下核心理念建立：

1. **权限控制必须分层：功能权限、数据权限、领域约束、敏感操作增强校验缺一不可**
2. **邮箱凭据、邮件正文、附件、审批结果和开放平台密钥必须作为高敏感资产重点保护**
3. **Open API 与 Webhook 必须具备签名、防重放、幂等、限流与审计能力**
4. **HTML 邮件与附件是主要攻击入口，必须落实清洗、扫描、隔离和访问留痕**
5. **高风险操作必须可追踪、可审计、可告警，避免“做了但查不到”**
6. **安全设计应从一开始嵌入领域模型和接口模型，而不是上线前补丁式加固**

通过本方案，系统能够在满足企业邮件协同、审批、开放集成需求的同时，建立起可实施、可审计、可演进的安全与权限基础体系。
