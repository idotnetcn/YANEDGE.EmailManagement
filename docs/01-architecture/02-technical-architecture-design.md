# 2. 架构设计背景

## 2.1 业务特征

邮件管理系统具有以下显著业务特征：

- 既有典型后台管理系统属性，也有准业务协同平台属性
- 数据既包含结构化元数据，也包含大文本正文和文件附件
- 对收件同步、发件重试、规则执行等异步任务依赖较强
- 既有用户交互型查询操作，也有长耗时后台处理任务
- 需要支持共享邮箱协同、审批、业务对象关联、审计留痕
- 需要开放 API 与 ERP / CRM / OA 等系统集成
- 需要满足企业级权限、安全与可追溯要求

## 2.2 技术挑战

从技术实现角度，系统主要挑战包括：

1. **邮件协议复杂性**
   需兼容 IMAP/SMTP，后续还需预留 Exchange、Graph API、Provider API 等接入扩展。

2. **异步处理复杂性**
   收件同步、发件、重试、Webhook 回调、统计汇总等不适合全部同步执行。

3. **大文本与附件处理复杂性**
   邮件正文可能为 HTML，附件体积可能较大，需要元数据与内容解耦。

4. **协同和权限复杂性**
   共享邮箱、组织范围、角色范围、负责人关系、审批关系共同决定数据可见性。

5. **系统集成复杂性**
   邮件系统既是业务系统，又是能力平台，必须保持内部稳定与对外低耦合。

## 2.3 架构目标

本系统架构设计应实现以下目标：

- 支持一期快速落地与稳定交付
- 保持代码结构清晰、职责边界明确
- 支持异步任务与后台处理
- 支持附件独立存储与安全访问
- 支持标准接口开放与事件回调
- 支持后续模块演进与服务拆分
- 满足企业级安全、审计与运维要求

# 3. 架构设计原则

## 3.1 模块化单体优先

一期采用**模块化单体（Modular Monolith）**架构，而不是直接上微服务。原因如下：

- 业务尚处于建设初期，边界虽可识别，但服务拆分时机未成熟
- 微服务会显著增加部署、治理、运维、分布式事务与一致性成本
- 模块化单体可在代码层面先形成清晰边界，为后续拆分打基础
- 对一期目标来说，模块化单体更利于交付效率、质量控制和团队协作

## 3.2 分层清晰、依赖单向

系统采用 ABP 推荐分层模式，保证：

- 表现层只依赖应用层
- 应用层协调业务用例，不直接承载复杂基础设施细节
- 领域层承载核心业务规则
- 基础设施层负责数据库、缓存、对象存储、邮件协议、外部系统接入
- 依赖方向稳定，避免循环依赖

## 3.3 领域边界先于技术边界

在拆模块、定表、写接口之前，先保证业务边界合理。
系统按“邮件、协同、规则、模板、关联、集成、安全审计”等领域划分模块，而不是按页面或 CRUD 生硬拆分。

## 3.4 同步简洁、异步优先

以下行为优先采用异步架构：

- 收件同步
- 发件执行
- 发件失败重试
- 附件扫描
- Webhook 回调
- 统计汇总
- 审计归档
- 搜索索引同步

这样可以避免用户请求链路过长，提升系统吞吐和稳定性。

## 3.5 元数据与内容分离

系统应将以下内容分开设计：

- 邮件元数据：主题、发件人、收件人、状态、关联关系等
- 邮件正文：HTML / Text 正文内容
- 附件元数据：名称、类型、大小、哈希、引用关系
- 附件内容：对象存储或文件存储中的二进制内容

该设计有利于：

- 控制数据库压力
- 降低大字段 IO
- 支持存储扩展
- 提高安全控制能力

## 3.6 平台能力前置

权限、审计、日志、配置、通知、健康检查等能力不应后补，而应作为架构底座统一设计。

# 4. 技术栈选型

## 4.1 后端技术栈

| 类别 | 选型 | 说明 |
|---|---|---|
| 运行时 | .NET 10.x | 与项目统一技术路线保持一致 |
| 应用框架 | ABP 10.x | 提供模块化、权限、审计、DDD、后台任务等能力 |
| ORM | EF Core | 与 ABP 集成成熟，适合 PostgreSQL |
| 数据库 | PostgreSQL | 开源稳定，支持 JSONB、全文检索、扩展性强 |
| 缓存 | Redis | 支持缓存、分布式锁、短期状态保存 |
| 后台任务 | Hangfire | 适合定时任务、重试任务、任务监控 |
| 对象存储 | MinIO / S3 兼容存储 | 用于附件与大对象管理 |
| 认证授权 | ABP Identity + OpenIddict / JWT | 支持本地认证与平台集成 |
| 日志 | Serilog | 结构化日志，便于检索与追踪 |
| API 文档 | Swagger / OpenAPI | 提供接口文档能力 |
| 容器化 | Docker | 统一部署交付 |
| 反向代理 | Nginx / Ingress | 统一入口与 TLS 终止 |

## 4.2 前端技术栈建议

虽然本文重点为后端架构，但为保证整体一致性，建议：

| 类别 | 选型 | 说明 |
|---|---|---|
| Web 前端 | Vue 3 / React 二选一 | 与团队能力保持一致 |
| 状态管理 | Pinia / Redux Toolkit | 管理页面状态 |
| UI 组件 | Ant Design Vue / Ant Design / Element Plus | 提高交付效率 |
| 富文本展示 | 安全 HTML 渲染 + sanitizer | 邮件正文展示 |
| 文件上传 | 分片上传组件（按需要） | 大附件支持预留 |

## 4.3 选型理由总结

### 4.3.1 选择 ABP 的原因
- 模块化支持较强
- 权限、审计、多组织等企业能力成熟
- 标准分层明确，适合复杂后台系统
- 易于沉淀统一工程规范

### 4.3.2 选择 PostgreSQL 的原因
- 支持 JSONB，适合邮件头信息、扩展元数据
- 可使用全文检索能力满足一期基础搜索
- 索引和事务能力成熟
- 运维成本与生态良好

### 4.3.3 选择 Hangfire 的原因
- 适合定时同步与重试型任务
- 有可视化后台，方便排障
- 与 .NET 生态集成成熟

### 4.3.4 选择对象存储的原因
- 附件不宜直接长期存于数据库大字段
- 易于扩展容量
- 便于做权限下载控制和生命周期管理

## 5.3 一期架构定位

一期不追求技术形态复杂化，而强调：

- 单体部署可控
- 模块边界清晰
- 异步能力完整
- 数据设计规范
- 可平滑演进

因此，一期默认部署形态为：

- 1 个 Web/API 应用
- 1 个后台任务执行器（可与 Web 合并或独立）
- 1 个 PostgreSQL
- 1 个 Redis
- 1 个对象存储
- 1 个 Nginx / Ingress

# 6. 分层架构设计

## 6.1 标准分层

建议采用 ABP 典型四层 + 横切能力结构：

```text
Presentation Layer（表现层）
Application Layer（应用层）
Domain Layer（领域层）
Infrastructure Layer（基础设施层）
```

横切能力：

- 权限与认证
- 审计与日志
- 配置与特性开关
- 缓存与锁
- 异常处理
- 通知与告警

## 6.2 表现层职责

表现层包含：

- Web API Controller
- DTO 输入输出
- 参数校验
- 权限校验入口
- API 版本路由
- Swagger 文档

职责边界：

- 不直接写复杂业务逻辑
- 不直接访问数据库
- 不直接调用第三方组件细节
- 只负责请求接入、参数转换和结果返回

## 6.3 应用层职责

应用层是业务用例编排层，负责：

- 执行业务流程
- 调用领域对象与仓储
- 事务边界控制
- 触发领域事件 / 集成事件
- DTO 与领域对象转换
- 权限与操作性校验

示例用例：

- 创建待发邮件
- 提交审批
- 执行认领
- 归档线程
- 手工重试发件
- 建立业务对象关联

## 6.4 领域层职责

领域层负责表达核心业务规则，包括：

- 聚合根
- 实体
- 值对象
- 领域服务
- 领域事件
- 规则校验器

领域层重点承载：

- 线程状态流转规则
- 审批约束规则
- 分派 / 认领规则
- 模板版本规则
- 规则命中后的业务动作模型
- 业务关联合法性约束

## 6.5 基础设施层职责

基础设施层负责：

- EF Core 仓储实现
- PostgreSQL 映射
- Redis 缓存实现
- 对象存储实现
- IMAP/SMTP 适配器
- Webhook 发送器
- Hangfire 任务实现
- 搜索实现
- 分布式锁实现
- 安全加密组件实现

# 7. 模块化架构设计

## 7.1 模块划分原则

模块划分遵循以下原则：

- 按业务领域划分，不按页面划分
- 模块内高内聚，模块间低耦合
- 共享能力尽量通过公共契约和事件交互
- 避免模块互相直接访问对方数据库细节

## 7.2 模块清单

一期建议划分如下模块：

| 模块 | 职责 |
|---|---|
| Identity / Organization | 用户、角色、组织、权限 |
| MailAccount | 邮箱账号接入、授权、同步配置 |
| MailMessage | 邮件主体、正文、收件人、头信息 |
| MailThread | 线程归并、线程状态、上下文 |
| MailCompose | 草稿、待发邮件、发件任务 |
| Collaboration | 分派、认领、转派、备注、待办 |
| Approval | 外发审批、审批记录 |
| Template | 模板、签名、变量 |
| RuleEngine | 自动分类、自动分派、黑白名单 |
| Attachment | 附件元数据、访问控制 |
| BusinessRelation | 联系人、客户、订单、合同等关联 |
| Integration | API 应用、Webhook、映射、集成日志 |
| Statistics | 报表、聚合统计、处理效率 |
| AuditSecurity | 审计、安全策略、敏感行为 |
| SystemSetting | 参数配置、通知配置、健康检查 |

## 7.3 模块依赖关系建议

```text
Identity / Organization
    ↑
SystemSetting
    ↑
MailAccount
    ↑
MailMessage ← MailCompose
    ↑            ↑
MailThread       │
    ↑            │
Collaboration    │
    ↑            │
Approval         │
    ↑            │
BusinessRelation │
    ↑            │
Template         │
RuleEngine       │
Attachment       │
Integration      │
Statistics       │
AuditSecurity    │
```

说明：

- `MailMessage`、`MailThread` 是邮件域核心模块
- `MailCompose` 侧重主动发件流程
- `Collaboration`、`Approval` 属于流程协同能力
- `BusinessRelation`、`Template`、`RuleEngine` 是增强能力
- `Integration`、`AuditSecurity`、`Statistics` 属于平台能力模块

## 7.4 模块交互方式

模块间交互优先顺序建议：

1. **应用层显式调用公共服务接口**
2. **发布领域事件 / 集成事件**
3. **共享只读查询服务**
4. **严禁直接跨模块修改内部实体**

例如：

- 邮件同步完成后发布 `MailReceivedEvent`
- 规则模块订阅后执行自动分类 / 自动分派
- 关联模块订阅后尝试业务对象匹配
- 统计模块订阅后更新聚合指标

# 8. 核心技术组件设计

## 8.1 邮件协议适配组件

### 8.1.1 组件职责
- 统一封装 IMAP 收件同步
- 统一封装 SMTP 发件
- 抽象 Provider API 接入能力
- 屏蔽不同邮件服务商差异

### 8.1.2 设计建议
定义统一适配接口，例如：

- `IMailInboxProvider`
- `IMailSendProvider`
- `IMailConnectionTester`
- `IMailCapabilityProvider`

通过账号配置决定实际使用哪种 Provider 实现。

### 8.1.3 一期支持策略
一期优先支持：

- IMAP 拉取邮件
- SMTP 发件

预留扩展：

- Exchange / EWS
- Microsoft Graph
- Gmail API
- 特定企业邮件服务 API

## 8.2 规则引擎组件

### 8.2.1 组件职责
- 对新邮件执行规则匹配
- 按优先级执行条件判断
- 输出规则命中日志
- 触发打标签、分派、归档等动作

### 8.2.2 设计原则
- 条件表达式可配置
- 动作类型可扩展
- 执行结果可审计
- 异常不影响主链路入库

## 8.3 模板渲染组件

### 8.3.1 组件职责
- 渲染邮件主题模板
- 渲染正文模板
- 组合签名
- 变量校验与替换

### 8.3.2 设计原则
- 模板引擎实现应安全可控
- 禁止执行任意脚本
- 变量缺失时支持降级策略
- 保留模板预览能力

## 8.4 附件存储组件

### 8.4.1 组件职责
- 附件元数据管理
- 文件上传 / 下载
- 对象存储路径规划
- 哈希去重预留
- 访问鉴权接入

### 8.4.2 路径设计建议
对象存储路径建议使用：

```text
/{environment}/{tenant-or-org}/{year}/{month}/{attachmentId}/{filename}
```

便于按环境、组织、时间管理。

## 8.5 审批组件

### 8.5.1 组件职责

- 创建审批单
- 流转审批状态
- 审批通过后触发发送

### 8.5.2 一期建议

# 9. 关键业务技术流程

## 9.1 收件同步技术流程

```text
Hangfire 定时触发
→ 扫描启用同步的邮箱账号
→ 获取邮箱锁（防止并发重复同步）
→ 建立 IMAP 连接
→ 拉取增量邮件 UID
→ 下载邮件头、正文、附件元数据
→ 解析 MIME 内容
→ 标准化地址、主题、Message-Id、References
→ 入库邮件元数据
→ 附件上传对象存储并写附件元数据
→ 执行线程归并
→ 发布 MailReceivedEvent
→ 规则引擎处理
→ 业务关联引擎处理
→ 统计更新
→ 记录同步任务结果
→ 释放锁
```

## 9.2 发件技术流程

```text
用户提交发件请求 / 外部系统创建待发邮件
→ 应用层校验权限、参数、模板、附件
→ 判断是否命中审批策略
→ 如需审批则创建审批单并结束同步请求
→ 审批通过后创建发件任务
→ Hangfire 执行发件任务
→ 读取发件邮箱配置
→ 调用 SMTP / Provider API
→ 更新发件任务状态
→ 生成已发送记录
→ 发布 MailSentEvent / MailSendFailedEvent
→ 触发 Webhook 与统计更新
```

## 9.3 线程归并流程

```text
新邮件入库
→ 读取 Message-Id / In-Reply-To / References
→ 优先按 RFC 头信息匹配线程
→ 若无法匹配则按标准化主题 + 参与人 + 时间窗口尝试归并
→ 若仍不匹配则创建新线程
→ 更新线程最后活动时间、参与人摘要、状态
```

## 9.4 协同处理流程

```text
线程创建或进入共享池
→ 规则引擎自动分派 / 用户人工认领
→ 更新当前负责人
→ 用户新增内部备注、转派、回复
→ 审批动作改变线程状态
→ 处理完成后归档
→ 审计与统计同步更新
```

## 9.5 Webhook 推送流程

```text
业务事件产生
→ 生成出站事件记录
→ 入队 Webhook 任务
→ 执行 HTTP 推送
→ 验签并等待响应
→ 成功则标记完成
→ 失败则按策略重试
→ 超过阈值后标记死信并告警
```

# 10. 数据与存储架构

## 10.1 数据分类

系统中的数据可分为四类：

| 数据类型 | 示例 | 存储方式 |
|---|---|---|
| 核心事务数据 | 邮件、线程、分派、审批、模板、规则 | PostgreSQL |
| 大文本数据 | HTML 正文、纯文本正文、原始头信息 | PostgreSQL / 分表设计 |
| 二进制对象 | 附件文件 | 对象存储 |
| 临时与高频状态数据 | 缓存、锁、短期令牌、限流计数 | Redis |

## 10.2 PostgreSQL 存储原则

### 10.2.1 核心原则
- 事务型数据优先入 PostgreSQL
- 能结构化的字段尽量结构化
- 扩展属性可使用 JSONB
- 大字段适度独立，避免主表膨胀
- 通过索引优化检索场景

### 10.2.2 大字段策略
建议拆分：

- 邮件主表：元数据字段
- 邮件正文表：HTML、Text、大头信息
- 附件表：元数据
- 附件对象：对象存储

### 10.2.3 JSONB 使用场景
适合存储：

- 标准化邮件头快照
- 原始 MIME 元数据摘要
- 外部业务对象扩展属性
- 规则执行上下文
- Webhook 载荷快照

## 10.3 对象存储原则

附件不直接长时间保存在数据库，采用对象存储，理由：

- 降低数据库膨胀
- 提升备份恢复灵活性
- 支持大容量文件
- 可配合 CDN / 预签名下载（如有需要）
- 易于后续生命周期管理

## 10.4 搜索策略

一期建议：

- PostgreSQL 普通索引 + 全文检索
- 针对主题、地址、标签、时间、状态建立索引
- 对正文建立基础全文搜索能力

二期可扩展：

- Elasticsearch / OpenSearch
- 附件全文索引
- OCR 与语义检索

# 11. 缓存与性能架构

## 11.1 缓存目标

缓存不是为“所有数据加速”，而是为高频读、低变化、重复计算结果服务。

## 11.2 缓存适用场景

建议缓存以下内容：

- 系统参数
- 邮箱连接配置摘要
- 模板渲染元信息
- 规则配置快照
- 组织权限摘要
- 用户可访问邮箱列表
- 常用统计聚合结果

## 11.3 不建议缓存的内容

以下内容不建议重缓存：

- 邮件详情正文
- 高频更新的线程状态
- 审批流程中的实时状态
- 权限敏感且变化频繁的细粒度结果

## 11.4 缓存策略

| 场景 | 建议策略 |
|---|---|
| 系统配置 | 读取缓存，更新主动失效 |
| 模板定义 | 读取缓存，发布新版本失效 |
| 规则快照 | 定时刷新 + 手工失效 |
| 权限摘要 | 登录或刷新时构建，短 TTL |
| 聚合统计 | 定时计算，查询缓存 |

## 11.5 分布式锁

以下场景建议使用 Redis 分布式锁：

- 同一邮箱同一时间仅允许一个同步任务执行
- 同一发件任务防重复发送
- 同一 Webhook 事件防重复推送
- 定时报表任务防重复执行

# 12. 异步任务与调度架构

## 12.1 异步任务场景

系统需异步处理的核心任务包括：

- 邮箱收件同步
- 发件任务执行
- 发件失败重试
- Webhook 推送
- 规则延迟处理
- 统计汇总
- 搜索索引同步
- 附件安全扫描（预留）
- 清理归档 / 生命周期任务（预留）

## 12.2 Hangfire 使用策略

一期建议采用 Hangfire，任务类型包括：

- Recurring Job：定时同步、统计计算、清理任务
- Background Job：发件、Webhook、索引更新
- Delayed Job：失败重试、延迟补偿

## 12.3 任务设计原则

### 12.3.1 幂等
每个任务都必须支持幂等设计，避免重复执行导致：

- 重复同步
- 重复发件
- 重复推送回调
- 重复统计

### 12.3.2 可重试
任务失败后应根据任务类型采用不同重试策略：

- 发件任务：短间隔有限次重试
- Webhook：指数退避重试
- 同步任务：下个周期继续尝试，重大故障告警
- 统计任务：允许下次补算

### 12.3.3 可观测
任务必须记录：

- 任务 ID
- 触发来源
- 开始时间
- 结束时间
- 结果
- 错误原因
- 重试次数

## 12.4 后台任务隔离建议

当系统规模变大时，可将：

- Web/API 进程
- 后台任务 Worker 进程

分开部署，以避免用户请求与后台任务争用资源。

# 14. 安全架构设计

## 14.1 安全目标

系统安全设计应覆盖：

- 身份认证
- 权限授权
- 数据访问控制
- 邮箱凭据保护
- 附件安全
- 审计追踪
- 接口安全
- 运维安全

## 14.2 认证架构

### 14.2.1 用户认证
- ABP Identity 管理用户
- 基于 Cookie + Token 或 JWT
- 支持后续接入统一身份平台

### 14.2.2 应用认证
- 外部系统通过 AppId / Secret 或 OAuth2 Client Credential 访问
- 不同应用配置不同作用域和权限

## 14.3 权限架构

权限模型应至少包括：

- 功能权限：是否可访问菜单、按钮
- 数据权限：可见哪些邮箱、线程、附件
- 操作权限：是否可删除、审批、下载附件
- 管理权限：是否可查看全部、配置规则、管理模板

## 14.4 数据权限架构

邮件数据可见性需综合以下因素判断：

- 邮箱授权范围
- 用户组织归属
- 线程参与关系
- 当前负责人
- 审批关系
- 管理员全局权限
- 业务对象数据权限映射

建议实现统一数据授权服务，而不是在每个查询页面手写判断。

## 14.5 邮箱凭据安全

邮箱密码 / AccessToken / RefreshToken 应满足：

- 加密存储
- 严禁明文日志输出
- 配置变更有审计
- 按最小权限原则管理访问

## 14.6 HTML 正文安全

邮件正文可能包含恶意内容，应对 HTML 做：

- 白名单标签保留
- script / style / 事件属性清理
- 外链资源风险控制
- iframe 等危险元素限制

## 14.7 附件安全

附件需支持：

- 鉴权下载
- 预留病毒扫描
- 哈希记录
- 敏感附件更高权限门槛
- 下载日志审计

## 14.8 接口安全

- 强制 HTTPS
- 限流与防刷
- 幂等校验
- 签名校验
- 参数校验
- 防越权检查
- 防止敏感信息泄露

# 17. 高可用与容灾设计

## 17.1 一期高可用策略

一期建议保证“关键组件可恢复、核心数据可备份、单点故障可替换”，不强制追求所有组件全冗余。

## 17.2 关键组件建议

### 17.2.1 Web/API
- 可多实例部署
- 无状态化
- 配置外部化

### 17.2.2 Worker
- 支持独立扩容
- 任务幂等，允许任务漂移
- 避免本地状态依赖

### 17.2.3 PostgreSQL
- 定期备份
- WAL 归档（按能力）
- 可选主从或托管数据库方案

### 17.2.4 Redis
- 用于缓存和锁，生产建议持久化或哨兵/集群视规模采用
- 若 Redis 故障，缓存可退化，锁相关任务需保护降级策略

### 17.2.5 对象存储
- 开启版本控制或定期备份策略
- 附件元数据与对象内容应可核对

## 17.3 备份策略建议

| 组件 | 备份建议 |
|---|---|
| PostgreSQL | 每日全量 + WAL / 增量 |
| 对象存储 | 每日快照 / 跨存储复制 |
| 应用配置 | 版本化配置中心或 GitOps |
| 审计日志 | 长期保留策略 |
| Hangfire 任务数据 | 与 PostgreSQL 一并备份 |

## 17.4 容灾恢复目标建议

| 指标 | 建议目标 |
|---|---|
| RPO | ≤ 15 分钟（视数据库备份策略） |
| RTO | ≤ 2 小时（一期建议） |

## 19.2 代码治理原则

- 领域层不依赖基础设施实现
- DTO 不泄漏到领域层
- Repository 查询不承载复杂业务规则
- 应用服务保持用例粒度，而不是大而全 Service
- 公共枚举、常量、错误码统一管理
- 所有跨模块能力通过接口或事件解耦

# 20. 技术风险与应对策略

## 20.1 邮件协议差异风险

**风险**：不同邮箱服务商兼容性差异明显。
**应对**：

- 抽象 Provider 接口
- 从 IMAP/SMTP 标准场景起步
- 增加连接测试与能力探测
- 将协议差异隔离在基础设施层

## 20.2 大附件与大文本性能风险

**风险**：邮件正文和附件导致查询慢、数据库膨胀。
**应对**：

- 正文表拆分
- 附件对象存储
- 列表只查摘要字段
- 详情按需加载正文与附件信息

## 20.3 线程归并误判风险

**风险**：按主题归并可能误关联。
**应对**：

- 优先 RFC 头信息归并
- 主题归并仅作为兜底
- 保留人工纠正机制
- 记录归并来源与规则

## 20.4 权限复杂度风险

**风险**：共享邮箱 + 组织 + 审批 + 负责人导致权限判断复杂。
**应对**：

- 建立统一授权服务
- 查询条件统一封装
- 高风险接口增加二次校验
- 审计所有敏感访问

## 20.5 异步任务积压风险

**风险**：高峰期收件同步、发件、回调任务堆积。
**应对**：

- Web 和 Worker 分离
- 任务分优先级队列
- 监控积压量
- 支持扩容 Worker

## 20.6 集成回调不稳定风险

**风险**：外部系统不可用导致 Webhook 长期失败。
**应对**：

- 回调记录落库
- 指数退避重试
- 死信机制
- 告警与人工补偿入口

# 21. 架构决策总结

## 21.1 关键架构决策

| 决策项 | 结论 |
|---|---|
| 架构形态 | 一期采用模块化单体 |
| 框架选型 | 采用 ABP 10.x |
| 数据库 | 采用 PostgreSQL |
| 缓存 | 采用 Redis |
| 任务调度 | 采用 Hangfire |
| 附件存储 | 采用 MinIO / S3 兼容对象存储 |
| 邮件接入 | 一期优先 IMAP + SMTP |
| 搜索策略 | 一期 PostgreSQL 基础搜索，后续可扩展 ES |
| 部署方式 | 容器化部署 |
| 安全策略 | 认证、权限、审计、附件鉴权、凭据加密前置 |

## 21.2 架构适用性评价

该架构方案适用于：

- 中小到中大型企业内部邮件协同平台
- 需要与 ERP / CRM / OA 集成的邮件能力中心
- 需要后续扩展为基础平台模块的系统
- 要求权限、安全、审计较强的企业应用场景

## 21.3 不建议场景

该一期架构暂不适合以下极端场景：

- 亿级邮件全文检索
- 超大规模实时营销群发平台
- 全球多地域低延迟跨区部署
- 完整替代专业邮件服务器产品

# 22. 结论

邮件管理系统的一期技术架构应采用：

**基于 ABP 的模块化单体架构 + PostgreSQL 核心数据存储 + Redis 缓存与锁 + 对象存储管理附件 + Hangfire 驱动异步任务 + 标准 API / Webhook 提供集成能力**

这一方案的核心价值在于：

1. **能快速落地，适合一期交付**
2. **模块边界清晰，便于团队协作开发**
3. **具备完整的异步任务和后台处理能力**
4. **兼顾权限、安全、审计和集成要求**
5. **能够从当前阶段平滑演进到更复杂的平台架构**

后续在业务规模扩大后，可按模块边界逐步拆分搜索、集成、附件、统计等能力服务，但在一期阶段，没有必要为了“技术先进感”提前引入高复杂度分布式架构。

该文档可作为后续数据库设计、领域模型设计、接口设计、部署方案和开发实施的基础依据。
