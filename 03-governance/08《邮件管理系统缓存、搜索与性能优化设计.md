# 1. 文档目标

本文档用于定义邮件管理系统在缓存、搜索与性能优化方面的整体设计方案，重点解决以下问题：

1. 哪些数据适合缓存，哪些不适合缓存
2. 缓存如何分层、如何命名、如何失效、如何避免脏读与雪崩
3. 邮件、线程、联系人、审批、规则等检索场景如何设计搜索能力
4. PostgreSQL 在高频列表查询、筛选、排序场景下如何建立索引
5. 详情页、附件预览、HTML 正文、发送任务、同步任务如何优化性能
6. Open API、Webhook、后台任务在高并发下如何保证稳定性
7. 系统如何建立性能监控、压测基线和持续调优机制

本文档的核心目标不是“盲目上缓存”，而是让系统在真实业务下具备：

- **查询更快**
- **写入可控**
- **搜索可用**
- **高峰期稳定**
- **问题可观测**
- **优化有依据**

# 3. 设计原则

## 3.1 先正确，再快

性能优化不能破坏业务一致性、权限隔离和安全要求。
例如：

- 线程列表可以缓存摘要，但不能因此绕过数据权限
- 附件预览地址可以短缓存，但不能变成长效公开链接
- 搜索结果可以异步索引，但不能返回用户无权访问的数据

## 3.2 读写分治

邮件系统天然存在以下特点：

- 读多写少：列表浏览、搜索、详情查看频次高
- 写入集中：同步入库、发件、审批、规则变更是写热点
- 大对象明显：HTML 正文、附件元数据、附件内容体积大

因此应采用：

- 读模型优化
- 热点缓存
- 异步索引
- 大对象延迟加载

## 3.3 分层缓存，不做“一把梭”

缓存不是只有 Redis。建议分层考虑：

- 浏览器端短缓存
- 应用内存缓存
- 分布式缓存
- 数据库物化/汇总表
- 搜索索引

每层解决的问题不同。

## 3.4 查询优化优先于缓存兜底

如果 SQL、索引、分页、本体模型设计很差，只靠缓存掩盖，最终会在：

- 缓存失效
- 冷启动
- 批量刷新
- 权限变化
- 复杂过滤

这些场景中暴露问题。

## 3.5 热点要保护，冷数据要归档

邮件系统运行久了以后，性能问题往往不是“单次查询慢”，而是：

- 历史数据膨胀
- 热点邮箱过热
- 某些线程被频繁访问
- 日志和审计表增长过快

因此必须同时考虑：

- 热点数据保护
- 历史数据归档
- 日志分层保留
- 统计数据汇总

## 3.6 可观测性先行

任何优化如果没有指标支撑，都是不可靠的。
必须建设：

- 查询耗时指标
- 缓存命中率
- 索引延迟
- 后台任务队列堆积
- API P95 / P99
- 错误率与超时率

# 4. 性能目标与容量假设

## 4.1 典型业务场景假设

以下为一期典型中型部署假设，实际项目可调整：

| 指标 | 假设值 |
|---|---|
| 邮箱账号数 | 100 ~ 1000 |
| 日均收件量 | 5万 ~ 50万 |
| 日均发件量 | 1万 ~ 10万 |
| 日均附件数 | 1万 ~ 5万 |
| 活跃用户数 | 500 ~ 3000 |
| 峰值并发在线用户 | 100 ~ 500 |
| Open API 峰值 QPS | 50 ~ 300 |
| Webhook 峰值投递 | 1000 ~ 10000 / 小时 |

## 4.2 关键性能目标建议

| 场景 | 目标 |
|---|---|
| 线程列表页首屏 | P95 < 800ms |
| 邮件详情页 | P95 < 1200ms |
| 工作台待办列表 | P95 < 500ms |
| 发件任务创建 | P95 < 500ms |
| Open API 创建待发邮件 | P95 < 700ms |
| 附件元数据查询 | P95 < 300ms |
| 附件下载令牌生成 | P95 < 200ms |
| 搜索建议接口 | P95 < 300ms |
| 统计 Dashboard | P95 < 1000ms |

## 4.3 后台处理目标建议

| 场景 | 目标 |
|---|---|
| 单账号同步作业延迟 | < 5 分钟 |
| 发件任务平均排队时间 | < 1 分钟 |
| Webhook 普通事件投递延迟 | < 30 秒 |
| 搜索索引延迟 | < 60 秒 |
| 缓存失效后重建 | 热点对象 < 3 秒 |

## 4.4 容量规划基本思路

一期建议以“**中等规模、可水平扩展**”为原则，设计如下能力：

- PostgreSQL 可承受高频分页查询与写入
- Redis 承担热点缓存、幂等、限流、短状态
- 后台任务队列处理同步、发件、索引、Webhook
- 搜索优先使用 PostgreSQL 能力，复杂全文检索场景可扩展至独立搜索引擎

# 5. 性能瓶颈分析总览

## 5.1 常见瓶颈点

邮件管理系统最常见性能瓶颈包括：

1. 线程列表多维筛选 + 排序 + 分页
2. 邮件详情一次性加载过多字段
3. HTML 正文与附件元数据过大
4. 权限过滤导致 SQL 复杂
5. 搜索使用 `%keyword%` 导致索引失效
6. 统计页实时聚合过重
7. 同步任务集中写入导致数据库压力上升
8. 发件、Webhook、索引更新叠加后台作业堆积
9. 热门共享邮箱成为访问热点
10. 审计、日志、访问记录表膨胀拖慢查询

## 5.2 典型高风险查询

以下查询需要重点优化：

- 我的待办线程列表
- 共享池待认领列表
- 线程详情 + 最近活动
- 邮件全文搜索
- 某邮箱最近 7 天统计
- 某附件访问日志
- 审批待办与历史列表
- 按外部业务引用查询发件任务

## 5.3 性能问题的根源分类

| 类型 | 示例 |
|---|---|
| 模型问题 | 一个接口返回过大对象图 |
| SQL 问题 | 排序字段无索引、深层 Join |
| 缓存问题 | 不该缓存的缓存了、该缓存的没缓存 |
| 搜索问题 | 把全文检索强行写成普通 SQL |
| 异步问题 | 所有后台任务共用同一低吞吐队列 |
| 资源问题 | 数据库连接池、线程池不足 |
| 热点问题 | 某共享邮箱、某线程被高频访问 |

# 6. 缓存架构设计

## 6.1 缓存分层建议

建议采用四层缓存思路：

```text
L0：前端/浏览器缓存（短时）
L1：应用进程内缓存（MemoryCache）
L2：分布式缓存（Redis）
L3：预计算/汇总表/搜索索引
```

## 6.2 各层职责

| 层级 | 主要用途 | 典型对象 |
|---|---|---|
| L0 浏览器缓存 | 静态字典、短期页面状态 | 枚举字典、标签配置 |
| L1 内存缓存 | 单节点高频只读数据 | 权限定义、模板摘要、规则开关 |
| L2 Redis | 多实例共享热点数据 | 线程摘要、统计缓存、幂等键 |
| L3 预计算层 | 复杂搜索与统计加速 | Dashboard 汇总、搜索索引 |

## 6.3 缓存使用原则

### 适合缓存
- 字典、枚举、配置项
- 模板摘要、签名摘要
- 热点线程摘要
- 权限快照摘要
- Dashboard 汇总结果
- Open API App 配置
- Webhook 订阅配置

### 不适合直接缓存
- 强一致要求极高且频繁变化的审批状态详情
- 权限变化非常频繁的明细列表结果
- 大体积 HTML 正文原文
- 大附件内容
- 需要复杂组合过滤的长列表全结果

# 7. 缓存对象分层设计

# 7.1 基础配置缓存

适用对象：

- 邮箱提供商配置
- 枚举字典
- 模板分类
- 标签定义
- 规则分类定义
- 签名模板摘要

特点：

- 变更低频
- 读取高频
- 可设置较长 TTL

建议：
- L1 + L2 双层缓存
- TTL：10 分钟 ~ 12 小时
- 更新时主动失效

## 7.2 权限与授权缓存

适用对象：

- 用户功能权限集合
- 用户可访问邮箱列表摘要
- 外部应用 scope 配置
- Webhook 订阅签名配置

特点：

- 读取高频
- 变更中低频
- 涉及安全，缓存必须保守

建议：
- 仅缓存摘要，不缓存过细业务状态
- TTL：1 ~ 10 分钟
- 权限变更后定向失效
- 禁止长期本地缓存导致越权延迟收敛

## 7.3 业务热点缓存

适用对象：

- 线程摘要
- 我的待办计数
- 邮箱健康状态
- Dashboard 汇总
- 最近联系人摘要
- 发件任务状态摘要

特点：

- 读取高频
- 可接受短时间最终一致
- 需要考虑热点保护

建议：
- 主要放 Redis
- TTL：30 秒 ~ 5 分钟
- 结合事件失效

## 7.4 搜索辅助缓存

适用对象：

- 搜索建议词
- 最近搜索历史
- 高频筛选条件结果计数
- 搜索配置元信息

特点：

- 命中率依赖关键词分布
- 不宜缓存大结果集
- 更适合缓存“小结果、小对象、小摘要”

建议：
- TTL：1 ~ 10 分钟
- 仅缓存前 N 个 suggestion 或计数摘要

## 7.5 防重与控制型缓存

适用对象：

- Idempotency-Key
- Open API Nonce
- 限流计数器
- 分布式锁
- 任务幂等执行状态

特点：

- 生命周期短
- 强依赖 Redis
- 直接影响稳定性

建议：
- TTL：分钟级到小时级
- 不与业务缓存混用命名空间

# 8. 缓存键规范与缓存模型

## 8.1 缓存键命名规范

建议格式：

```text
mailmgmt:{env}:{module}:{resource}:{key}
```

示例：

```text
mailmgmt:prod:dict:tags:all
mailmgmt:prod:thread:summary:{threadId}
mailmgmt:prod:user:todo-count:{userId}
mailmgmt:prod:account:health:{accountId}
mailmgmt:prod:openapi:app:{appKey}
mailmgmt:prod:idempotency:send:{idempotencyKey}
mailmgmt:prod:nonce:{appKey}:{nonce}
```

## 8.2 键设计原则

- 包含环境前缀，避免串环境
- 模块清晰，方便批量清理
- 不使用过长原始 JSON 作为键
- 用户输入类关键词建议哈希化
- 避免高基数无界增长

## 8.3 缓存值结构建议

缓存值建议使用轻量 DTO，而不是直接缓存 ORM 实体。
例如线程摘要缓存：

```json
{
  "threadId": "uuid",
  "subject": "报价确认",
  "threadStatus": 2,
  "latestMessageTime": "2026-04-26T08:00:00Z",
  "unreadCount": 1,
  "currentAssignee": {
    "id": "uuid-user",
    "name": "张三"
  },
  "version": 12
}
```

## 8.4 TTL 建议表

| 对象 | TTL 建议 |
|---|---|
| 字典/枚举 | 1h ~ 12h |
| 模板摘要 | 10m ~ 1h |
| 线程摘要 | 30s ~ 5m |
| 工作台计数 | 15s ~ 60s |
| Dashboard 汇总 | 30s ~ 5m |
| 邮箱健康状态 | 30s ~ 2m |
| 搜索建议 | 1m ~ 10m |
| App 配置 | 5m ~ 30m |
| Idempotency-Key | 24h ~ 72h |
| Nonce | 5m ~ 10m |

# 9. 缓存更新与失效策略

## 9.1 失效优先于复杂强刷

优先采用：

- 更新业务数据后删除缓存
- 下次读取自动重建

而不是所有场景都强制同步更新缓存值。
因为后者更复杂，更容易产生遗漏和脏数据。

## 9.2 常见策略

### 9.2.1 Cache Aside
最适合：

- 线程摘要
- 模板摘要
- 工作台统计
- 联系人摘要

流程：

```text
读：先查缓存，未命中再查库并写缓存
写：先写库，再删缓存
```

### 9.2.2 Write Through
适合极少数写入路径统一、读频高的对象。
本系统中一般不作为主流方案。

### 9.2.3 Write Behind
不建议用于核心业务对象，避免一致性与丢数据风险。

## 9.3 事件驱动失效建议

当以下事件发生时，应定向清理相关缓存：

| 事件 | 应清理缓存 |
|---|---|
| 新邮件归入线程 | 线程摘要、未读计数、工作台计数 |
| 线程认领/转派 | 线程摘要、我的待办、共享池列表计数 |
| 发件成功/失败 | 发件任务状态、线程摘要、Dashboard |
| 审批通过/拒绝 | 审批待办计数、发件任务摘要 |
| 模板发布 | 模板详情与摘要缓存 |
| 规则启停 | 规则摘要、规则列表 |
| 权限变更 | 用户权限快照、邮箱授权快照 |
| AppSecret 轮换 | Open API App 配置缓存 |
| Webhook 订阅变更 | 订阅缓存 |

## 9.4 随机过期时间

为避免缓存同一时刻大量失效，建议 TTL 增加随机抖动：

```text
baseTTL + random(0, jitter)
```

例如：
- 5 分钟基础 TTL + 0~60 秒抖动

# 10. 缓存一致性设计

## 10.1 一致性目标

邮件系统缓存通常采用**最终一致**，但不同对象一致性要求不同：

| 对象 | 一致性要求 |
|---|---|
| 用户权限快照 | 高 |
| 发件任务最终状态 | 高 |
| 线程摘要 | 中 |
| Dashboard 汇总 | 中低 |
| 搜索建议词 | 低 |

## 10.2 防止脏缓存

建议采用以下手段：

1. 更新数据库成功后再删除缓存
2. 使用版本号或更新时间戳辅助判断
3. 避免并发回填旧值
4. 热点对象使用单飞策略防击穿

## 10.3 防缓存击穿

对热点线程、热点统计数据，建议：

- Redis 未命中时加短分布式锁
- 只允许一个请求回源重建
- 其他请求短等待或返回旧值

## 10.4 防缓存穿透

对于不存在对象：

- 对“空结果”短缓存
- 如无此 `threadId` / `attachmentId`，缓存空标记 30~120 秒
- 结合参数合法性校验和限流

## 10.5 防缓存雪崩

- 过期时间随机化
- 热点对象预热
- 多级缓存
- 高峰前预加载 Dashboard / 配置缓存
- Redis 故障时允许部分接口降级

# 11. 搜索架构设计

## 11.1 搜索需求分类

邮件管理系统搜索需求一般分为四类：

1. **结构化筛选**
   - 按状态、邮箱、负责人、时间、是否有附件筛选

2. **轻量关键词检索**
   - 主题、发件人、收件人、业务编号

3. **全文搜索**
   - 邮件正文、内部备注、模板内容

4. **搜索建议与联想**
   - 最近联系人、客户名、业务编号建议

## 11.2 一期搜索架构建议

一期建议采取“**PostgreSQL 为主，搜索引擎可扩展**”路线：

### 方案 A：PostgreSQL 优先
适用于：
- 规模中等
- 搜索复杂度可控
- 主要是结构化 + 轻全文

可使用：
- B-Tree 索引
- GIN 索引
- trigram
- tsvector 全文搜索

### 方案 B：引入独立搜索引擎
适用于：
- 正文全文检索要求高
- 多字段相关度排序复杂
- 数据量上百万到千万级
- 搜索高亮、模糊匹配要求强

可选：
- Elasticsearch / OpenSearch

## 11.3 一期建议结论

建议一期默认采用：

- PostgreSQL 结构化筛选 + 部分全文搜索
- 搜索索引表 / 物化列辅助
- 预留独立搜索引擎接口抽象

原因：
- 降低运维复杂度
- 足以支撑一期业务
- 后续可平滑扩展

# 13. 查询场景优化设计

# 13.1 线程列表查询优化

线程列表是系统最核心高频查询。优化要点：

1. 只查列表所需字段
2. 避免一次加载全部邮件正文
3. 权限过滤前置
4. 分页使用稳定排序字段
5. 复杂统计字段尽量预计算

建议返回字段：
- `id`
- `subject`
- `threadStatus`
- `latestMessageTime`
- `unreadCount`
- `currentAssignee`
- `hasAttachment`
- `messageCount`
- `businessSummary`

不建议列表直接返回：
- HTML 正文
- 全量参与人明细
- 全量活动时间线
- 审批完整历史

## 13.2 工作台待办查询优化

“我的待办”是典型热点查询。建议：

- 建立单独查询视图或读模型
- 按 `assignee_id + status + due_time` 建索引
- 待办计数单独缓存
- 列表与计数分开查询，避免一条 SQL 做完所有事情

## 13.3 审批列表查询优化

审批列表典型筛选字段：

- 当前审批人
- 状态
- 提交时间
- 业务类型

建议：
- 建复合索引
- 审批流程步骤摘要冗余到主表
- 详情页再查审批记录明细

## 13.4 发件任务查询优化

常见查询：

- 按状态查失败任务
- 按创建人查我的草稿
- 按外部业务引用查任务

建议：
- `external_biz_ref` 建唯一索引或高选择性索引
- `status + created_time` 复合索引
- 失败重试查询单独优化

## 13.5 统计 Dashboard 查询优化

Dashboard 不建议每次实时全表聚合。
建议：

- 按小时/天预汇总
- Redis 短缓存
- 局部实时 + 历史汇总结合

例如：
- 今日待办数实时计算
- 历史趋势图读汇总表

# 14. PostgreSQL 索引与数据访问优化

# 14.1 索引设计原则

- 索引服务于查询，不为“看起来完整”而建
- 索引字段顺序与查询条件顺序一致
- 避免冗余和重复索引
- 高写入表索引不能过多
- 定期审查慢查询与未使用索引

## 14.2 典型表索引建议

## 14.2.1 `mail_thread`
建议索引：

- `idx_mail_thread_account_status_latest_time`
  - `(mail_account_id, thread_status, latest_message_time desc)`

- `idx_mail_thread_assignee_status_latest_time`
  - `(current_assignee_id, thread_status, latest_message_time desc)`

- `idx_mail_thread_latest_time`
  - `(latest_message_time desc)`

- `idx_mail_thread_has_attachment`
  - `(has_attachment)`

- `idx_mail_thread_search_vector`
  - `GIN(search_vector)`

## 14.2.2 `mail_message`
建议索引：

- `idx_mail_message_thread_sent_time`
  - `(thread_id, sent_time asc)`

- `idx_mail_message_account_received_time`
  - `(mail_account_id, received_time desc)`

- `idx_mail_message_internet_message_id`
  - `(internet_message_id)`

- `idx_mail_message_search_vector`
  - `GIN(search_vector)`

## 14.2.3 `mail_send_task`
建议索引：

- `idx_mail_send_task_status_created_time`
  - `(status, creation_time desc)`

- `idx_mail_send_task_creator_status`
  - `(creator_id, status, creation_time desc)`

- `uk_mail_send_task_external_biz_ref`
  - `(external_biz_ref)` 唯一或高选择性索引

## 14.2.4 `mail_approval`
建议索引：

- `idx_mail_approval_current_approver_status`
  - `(current_approver_id, status, submitted_time desc)`

- `idx_mail_approval_business_type_business_id`
  - `(business_type, business_id)`

## 14.2.5 `mail_attachment`
建议索引：

- `idx_mail_attachment_message_id`
  - `(message_id)`

- `idx_mail_attachment_thread_id`
  - `(thread_id)`

- `idx_mail_attachment_sensitive`
  - `(is_sensitive)`

## 14.2.6 `mail_internal_note`
建议索引：

- `idx_mail_internal_note_thread_id_created_time`
  - `(thread_id, creation_time desc)`

## 14.2.7 审计与访问日志表
高增长日志表建议：

- 按时间索引
- 结合分区表设计
- 避免过多二级索引

## 14.3 查询优化建议

### 避免
- `SELECT *`
- 深层多表 Join 再分页
- 对大字段排序
- `LIKE '%keyword%'` 全场景硬查
- 一次查询把详情页所有子对象全带出

### 建议
- 显式字段投影
- 先分页主键再回表
- 大对象延迟加载
- 高频列表使用读模型 DTO
- 使用 `AsNoTracking`

## 14.4 分页优化建议

优先建议：

### 普通管理页
- 使用 `OFFSET/LIMIT`
- 页面不深时可接受

### 深分页或滚动加载场景
- 使用 Keyset Pagination（基于时间+ID 游标）
- 适合“最近邮件”“最近线程”这类场景

示例排序键：
- `latest_message_time desc, id desc`

## 14.5 分区建议

对以下超大表可考虑按月分区：

- `mail_message`
- `mail_attachment_access_log`
- `audit_operation_log`
- `integration_api_call_log`
- `webhook_delivery_log`

目的：
- 提升归档与清理效率
- 降低大表扫描代价
- 便于冷热分离

# 15. 列表页与详情页性能优化

# 15.1 列表页优化原则

列表页的关键不是“查得全”，而是“查得快”。
建议：

- 列表页仅返回摘要
- 详情页按需补全
- 统计数字异步或单独接口获取
- 同页避免多个重量接口并发打库

## 15.2 线程详情页优化

线程详情页通常包括：

- 线程摘要
- 邮件列表
- 当前负责人
- 业务关联
- 内部备注
- 活动时间线
- 审批摘要

不建议首屏一次性同步加载全部模块。
建议拆分为：

1. 首屏主接口：线程摘要 + 最近邮件摘要
2. 二级接口：活动时间线
3. 二级接口：内部备注
4. 二级接口：审批历史
5. 附件按用户操作加载

## 15.3 邮件详情页优化

邮件详情建议分层加载：

### 首屏返回
- 主题
- 发件人/收件人摘要
- 时间
- 正文纯文本摘要或清洗后 HTML
- 附件列表摘要

### 延迟返回
- 原始头信息
- 大正文原文
- 全量收件人明细
- 关联审计信息

## 15.4 Dashboard 优化

Dashboard 常见错误是“一页十几个统计卡片，每个都打一次库”。
建议：

- 聚合成单接口
- 使用汇总表 + Redis 缓存
- 对趋势图采用按天预聚合
- 高峰时允许 30~60 秒延迟

# 16. 附件、正文与大对象处理优化

# 16.1 基本原则

附件与正文是系统最重的数据对象，不应在普通查询中滥用加载。

## 16.2 正文处理优化

建议正文存储分为：

- 原始 HTML
- 清洗后 HTML
- 纯文本摘要
- 短摘要字段

查询策略：

| 场景 | 加载内容 |
|---|---|
| 列表页 | 摘要字段 |
| 详情页首屏 | 清洗后 HTML 或纯文本 |
| 调试/原文查看 | 原始 HTML，按需加载 |

## 16.3 附件处理优化

不建议：
- 把附件内容直接存数据库大字段供在线频繁读取
- 列表页直接返回所有附件详情

建议：
- 文件体存对象存储
- 数据库保存元数据
- 下载走短期签名 URL 或代理流式输出
- 预览地址短时缓存
- 文件哈希、大小、MIME 独立存储

## 16.4 图片与内联资源处理

HTML 邮件中经常包含内联图片。建议：

- 首屏不加载全部外链资源
- 对内联附件与普通附件区分
- 预览走受控代理
- 可异步生成缩略图/预览版本

## 16.5 大对象懒加载

以下字段建议懒加载：

- `raw_html_body`
- `mime_source`
- `raw_headers`
- 大型审批快照
- 大型变更 JSON

# 17. 异步任务与后台处理性能设计

# 17.1 后台任务类型划分

建议将后台任务按类型分队列：

- 邮箱同步队列
- 发件执行队列
- 搜索索引队列
- Webhook 投递队列
- 统计汇总队列
- 清理归档队列

## 17.2 为什么要分队列

如果所有任务混在一个队列中，会出现：

- 大量同步任务堵住发件任务
- Webhook 重试挤占核心业务
- 索引更新拖慢用户可见操作

因此建议至少逻辑隔离。

## 17.3 同步任务优化

邮箱同步任务建议：

- 按邮箱账号粒度串行或有限并行
- 单邮箱内部按文件夹顺序或有限并发
- 支持增量同步
- 记录断点（UID / 历史游标）
- 批量入库，减少逐条事务

## 17.4 发件任务优化

发件任务建议：

- 按邮箱账号或发件通道限并发
- 对 SMTP 临时失败支持退避重试
- 用状态机避免重复发送
- 批量高峰时平滑调度，避免瞬时打爆发件通道

## 17.5 索引更新优化

搜索索引更新建议：

- 合并同一线程短时间内多次变更
- 批处理更新
- 限制单批次大小
- 失败后进入重试队列

## 17.6 Webhook 投递优化

Webhook 建议：

- 独立异步队列
- 并发受控
- 按订阅方限速
- 指数退避重试
- 支持死信队列

# 18. Open API 与 Webhook 性能设计

# 18.1 Open API 性能特点

Open API 的压力主要体现在：

- 高频短请求
- 幂等校验
- 签名校验
- 外部系统重试
- 外部引用查询

建议重点优化：

- App 配置缓存
- Nonce 去重 Redis 化
- 幂等键 Redis 化
- 请求体校验快速失败
- 写库逻辑短事务

## 18.2 Open API 创建待发邮件优化

流程建议：

```text
鉴权
→ Nonce/签名校验
→ 幂等校验
→ 基础参数校验
→ 写 send_task 主数据
→ 异步处理附件绑定/索引更新/通知
→ 快速返回
```

不要在同步请求中做过多后处理。

## 18.3 Webhook 投递性能优化

建议：
- 投递日志先写入数据库或队列
- 实际 HTTP 投递异步执行
- 响应超时要明确配置
- 不同订阅方隔离重试影响
- 批量事件不要在单线程串行阻塞

## 18.4 外部查询接口优化

高频查询如：

- 按 `externalBizRef` 查发件任务
- 查审批状态
- 查事件投递结果

建议：
- 唯一索引
- 热点短缓存
- DTO 直出，不加载内部复杂对象

# 19. 并发控制与热点保护

# 19.1 热点场景识别

热点通常出现在：

- 共享客服邮箱
- 某大客户线程
- Dashboard 首页
- “我的待办”计数
- 高频 Open API 应用
- 某些热门附件下载

## 19.2 热点线程保护

对热点线程详情建议：

- 线程摘要 Redis 缓存
- 活动时间线分页加载
- 附件列表按需获取
- 并发读情况下启用短本地缓存

## 19.3 认领/转派并发控制

认领线程、审批通过等强状态动作建议：

- 数据库乐观锁版本号
- 或状态条件更新
- 冲突返回明确业务错误

例如：
```sql
update mail_thread
set current_assignee_id = @userId, version = version + 1
where id = @threadId
  and thread_status = @claimableStatus
  and version = @expectedVersion;
```

## 19.4 分布式锁使用边界

可用于：
- 热点缓存重建
- 单账号同步互斥
- 关键周期任务去重

不建议滥用：
- 普通业务每次写操作都上 Redis 锁
- 可以由数据库状态机解决的问题

## 19.5 批量写入保护

同步入库、日志写入、Webhook 批量投递应支持：

- 批量处理
- 批次大小限制
- 背压
- 失败重试队列

# 20. 限流、降级与熔断设计

# 20.1 限流目标

限流是为了保护系统，而不是“卡用户”。
建议限流对象包括：

- 登录接口
- Open API 写接口
- 全文搜索接口
- 附件下载接口
- 手工同步接口
- Webhook 重推接口

## 20.2 限流维度建议

| 维度 | 场景 |
|---|---|
| 用户维度 | 搜索、下载、工作台操作 |
| 应用维度 | Open API |
| IP 维度 | 登录、下载、Webhook 管理 |
| 邮箱账号维度 | 同步、发件 |
| 订阅方维度 | Webhook 投递 |

## 20.3 降级策略建议

当 Redis、搜索、统计服务压力异常时，可采用：

### 轻降级
- Dashboard 返回缓存旧值
- 搜索建议关闭高亮或联想
- 附件访问日志异步补写

### 中降级
- 暂停非核心统计刷新
- 暂停低优先级索引更新
- 限制深分页搜索

### 重降级
- 暂停手工同步
- 暂停批量导出
- 限制 Open API 非核心写请求

## 20.4 熔断策略建议

对外部依赖如：

- SMTP
- IMAP
- 病毒扫描服务
- 预览转换服务
- Webhook 外部回调

建议：
- 超时控制
- 失败阈值熔断
- 半开恢复探测
- 明确 fallback

# 21. 读写分离与扩展建议

# 21.1 一期建议

一期若规模适中，可先采用单主 PostgreSQL + Redis 的模式，但要预留读写扩展能力。

## 21.2 后续扩展方向

### 数据库层
- 主从复制
- 读写分离
- 分区表
- 历史归档库

### 缓存层
- Redis 高可用
- 热点键治理
- 缓存命名空间分模块

### 搜索层
- PostgreSQL 全文 → 独立搜索引擎
- 搜索异步索引流水线

### 文件层
- 对象存储独立扩展
- 预览服务独立部署

## 21.3 读写分离使用建议

适合走只读副本的场景：

- 统计查询
- 历史列表
- 审计日志查询
- 搜索辅助查询

不建议立即走只读副本的场景：

- 刚写后立刻读的一致性敏感查询
- 认领、审批、发件状态变更校验

# 22. 监控指标与性能观测设计

# 22.1 核心观测目标

系统必须可以回答：

- 哪个接口慢
- 哪类查询慢
- 缓存是否命中
- Redis 是否成为瓶颈
- 搜索索引是否延迟
- 哪个后台队列积压
- 附件下载是否异常高峰

## 22.6 后台任务指标建议

# 23. 压测与容量评估建议

# 23.1 压测目标

压测不仅要看“系统能不能跑”，更要看：

- 高峰时哪里最先出问题
- 延迟拐点在哪里
- 缓存是否有效
- 数据库索引是否合理
- 队列是否会堆积

## 23.2 重点压测场景

### 场景 1：线程列表
- 多筛选条件
- 多用户并发
- 测 P95 / P99

### 场景 2：邮件详情
- 带正文摘要
- 带附件元数据
- 观察数据库与对象存储压力

### 场景 3：Open API 创建待发邮件
- 带签名、幂等、附件元数据
- 观察 Redis、数据库、任务队列压力

### 场景 4：同步高峰
- 多邮箱同时同步
- 观察批量写入与索引更新延迟

### 场景 5：Webhook 批量投递
- 模拟外部超时与失败
- 观察重试队列堆积

## 23.3 压测指标建议

- QPS / TPS
- P50 / P95 / P99
- CPU / 内存
- GC 次数与耗时
- 数据库连接池占用
- Redis 命令耗时
- 队列堆积
- 错误率 / 超时率

## 23.4 容量评估建议

建议按以下增长维度做容量预测：

- 日新增邮件数
- 日新增附件数
- 活跃线程数
- 热点邮箱数
- 附件对象存储增长
- 审计日志增长
- 搜索索引增长

# 25. ABP 与 .NET 落地建议

# 25.1 缓存实现建议

建议使用：

- `IDistributedCache<T>` 承担分布式缓存
- `IMemoryCache` 承担本地热点缓存
- 自定义 `ICacheKeyNormalizer` 统一键命名
- 封装 `ICacheService` 统一 TTL、抖动、日志

## 25.2 查询实现建议

### 对高频列表查询
不要直接返回实体。建议：

- 使用 QueryService
- 显式 Select 投影 DTO
- `AsNoTracking`
- 避免 AutoMapper 在大列表上隐式加载导航属性

## 25.3 EF Core 优化建议

- 使用 `AsNoTracking`
- 避免不必要 Include
- 大列表分页先排序再投影
- 关键查询编写编译查询或显式 SQL（按需）
- 对热点查询进行 SQL 分析与 explain 审查

## 25.4 后台任务建议

可基于：

- ABP Background Jobs
- 或独立作业框架（按项目选型）

建议按队列区分：
- Sync
- Send
- SearchIndex
- Webhook
- Statistics

## 25.5 搜索抽象建议

建议定义统一接口：

- `IMailSearchService`
- `IThreadSearchService`
- `IMessageSearchService`
- `ISearchIndexUpdater`

这样后续可从 PostgreSQL 平滑切换到独立搜索引擎实现。

## 25.6 监控落地建议

建议接入：

- OpenTelemetry Metrics / Traces
- ASP.NET Core 请求指标
- EF Core SQL 日志
- Redis 访问指标
- 后台任务耗时与队列长度指标

## 25.7 建议组件接口

可定义：

- `IThreadSummaryCacheService`
- `IUserWorkbenchCacheService`
- `IDashboardMetricsCacheService`
- `ISearchSuggestionCacheService`
- `IIdempotencyStore`
- `INonceStore`
- `IHotKeyProtectionService`

# 26. 结论

邮件管理系统的缓存、搜索与性能优化设计，应围绕以下核心理念建立：

1. **性能优化必须以正确的数据模型、查询模型和权限模型为前提**
2. **缓存要分层、分对象、分一致性要求，不应一刀切**
3. **高频列表、工作台、Dashboard、Open API 是一期最值得投入优化的场景**
4. **全文搜索应采用可演进架构：一期基于 PostgreSQL，后续平滑扩展到独立搜索引擎**
5. **附件、HTML 正文、审计日志等大对象必须延迟加载、隔离访问、避免主链路过载**
6. **后台任务必须队列化、分级化、可监控，避免同步、发件、索引、Webhook 相互拖垮**
7. **任何性能方案都必须建立在慢查询分析、缓存命中率、队列堆积、接口 P95/P99 等指标基础之上**

通过本方案，系统能够在满足邮件协同、审批、开放集成与历史沉淀场景的同时，建立起可持续演进、可测量、可定位、可扩展的性能基础体系。
