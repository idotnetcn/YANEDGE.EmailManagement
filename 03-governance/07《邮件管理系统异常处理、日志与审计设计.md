# 1. 文档目标

本文档用于明确邮件管理系统在以下方面的统一设计规范：

1. 异常如何分类、抛出、转换和返回
2. 日志如何分级、记录、检索和告警
3. 审计如何覆盖高风险业务动作与关键安全事件
4. 如何确保接口异常响应稳定、日志可追踪、审计可归责
5. 如何支撑开发调试、生产运维、安全检查和问题追踪

本文档的核心目标是让系统具备以下能力：

- **出了问题能快速定位**
- **发生异常能准确反馈**
- **高风险行为能完整留痕**
- **调用链路能跨模块串起来**
- **日志足够有用，但不会泄露敏感信息**

本文档是以下工作的直接输入：

- API 全局异常处理中间件实现
- 业务异常与错误码设计
- 日志组件与日志格式统一
- 审计表结构与审计服务实现
- 监控告警规则配置
- 安全审计与运维排障

# 3. 设计原则

## 3.1 异常要有业务语义

异常不是“报错文本”，而是系统状态与业务规则的表达。
例如：

- “线程状态不允许归档”
- “当前用户不是审批人”
- “附件无权下载”

这些都应是明确的业务异常，而不是模糊的 `Exception("操作失败")`。

## 3.2 对外返回稳定，对内保留足够上下文

对外接口返回的结构、错误码、提示语必须稳定。
对内日志则需要保留足够信息用于排查：

- TraceId
- 资源 ID
- 用户 ID
- 邮箱 ID
- 线程 ID
- 发件任务 ID
- 远程调用信息
- 原始异常栈

## 3.3 不把可预期业务问题当系统故障

例如：

- 审批状态非法
- 重试次数超限
- 非当前负责人转派
- 邮箱已禁用

这些都是**可预期业务异常**，应按业务错误返回，而不是记成系统级 Error 并污染告警。

## 3.4 日志是资产，不是垃圾堆

日志必须做到：

- 有结构
- 有上下文
- 有筛选价值
- 有保留策略
- 不记录无意义重复信息

避免：

- 大量 `Console.WriteLine`
- 无 TraceId
- 无业务上下文
- 所有日志都打 `Error`
- 把整个请求体原样打日志

## 3.5 审计优先覆盖高风险动作

并非所有行为都要审计，但以下必须优先保障：

- 配置变更
- 发件
- 审批
- 附件访问
- 权限变更
- Open API 写操作
- Webhook 配置与重推
- 敏感对象访问

## 3.6 敏感信息最小暴露

日志和异常处理中禁止输出：

- 邮箱密码
- AccessToken / RefreshToken
- AppSecret
- Webhook Secret
- 敏感附件临时签名地址
- 全量 HTML 正文
- 完整个人隐私数据

# 4. 异常体系设计

## 4.1 异常体系目标

系统异常体系应满足：

1. 开发者能够快速识别异常类型
2. 前端和第三方系统能够稳定处理错误响应
3. 运维能够区分业务失败、依赖失败、系统故障
4. 安全团队能够基于异常识别攻击与滥用行为

## 4.2 异常分层

建议将异常按层次划分为：

```text
表示层异常（接口入参、认证、授权）
应用层异常（用例执行、编排失败）
领域层异常（业务规则、不变量、状态机）
基础设施异常（数据库、缓存、对象存储、SMTP/IMAP、HTTP）
集成异常（Open API、Webhook、第三方服务）
系统异常（未知未处理异常）
```

## 4.3 异常基类建议

建议建立统一异常抽象：

- `MailManagementException`：系统业务异常基类
- `MailBusinessException`：业务规则异常
- `MailAuthorizationException`：授权失败异常
- `MailValidationException`：参数/数据校验异常
- `MailIntegrationException`：外部集成异常
- `MailInfrastructureException`：基础设施异常
- `MailTransientException`：可重试临时异常
- `MailFatalException`：严重不可恢复异常

# 5. 异常分类与分级

## 5.1 异常分类

### 5.1.1 参数与输入异常
典型场景：

- 必填项缺失
- 枚举值非法
- 分页参数越界
- 变量模板渲染缺少关键参数

### 5.1.2 认证异常
典型场景：

- Token 无效
- 签名错误
- 时间戳过期
- Nonce 重放

### 5.1.3 授权异常
典型场景：

- 无权限查看线程
- 无权限下载附件
- 非审批人尝试审批

### 5.1.4 业务规则异常
典型场景：

- 已归档线程不可继续分派
- 发件任务状态非法
- 审批单已撤回不可继续审批
- 邮箱已禁用不可发件

### 5.1.5 依赖资源异常
典型场景：

- 数据库连接失败
- Redis 不可用
- 对象存储下载失败
- SMTP 连接异常
- IMAP 同步超时

### 5.1.6 集成异常
典型场景：

- Open API 签名校验失败
- Webhook 多次投递失败
- 调用外部业务接口超时

### 5.1.7 未知异常
典型场景：

- 空引用
- 序列化异常
- 未考虑分支导致的运行时异常

## 5.2 异常分级建议

| 级别 | 说明 | 示例 |
|---|---|---|
| L1 提示级 | 预期内普通业务失败 | 当前线程不可认领 |
| L2 警告级 | 需要关注但不影响系统整体 | 单次 Webhook 投递失败 |
| L3 错误级 | 某功能调用失败，需要处理 | SMTP 发件失败、数据库事务失败 |
| L4 严重级 | 核心链路故障或安全风险 | 凭据解密失败、审批绕过疑似、批量发件异常 |

## 5.3 是否可重试维度

异常还应增加“是否可重试”属性：

| 类型 | 是否可重试 |
|---|---|
| 参数错误 | 否 |
| 授权失败 | 否 |
| 业务状态冲突 | 否/视场景 |
| 网络超时 | 是 |
| 数据库瞬时连接失败 | 是 |
| SMTP 临时拒信 | 是 |
| 对象存储服务不可达 | 是 |
| 配置缺失 | 否 |

# 6. 统一异常处理机制

## 6.1 总体处理流程

建议所有未在业务代码中明确处理的异常统一进入全局异常处理组件，处理流程如下：

```text
请求进入
→ 参数校验
→ 应用服务执行
→ 发生异常
→ 异常分类与映射
→ 记录日志
→ 生成标准错误响应
→ 输出 traceId
```

## 6.2 处理层次建议

### 6.2.1 Controller / HttpApi 层
不做大量 try-catch。
优先依赖：

- 参数校验机制
- 权限校验机制
- 全局异常中间件/过滤器

### 6.2.2 Application 层
可在必要时捕获并转换异常，例如：

- 外部服务异常转业务可理解异常
- 幂等冲突转 409
- 模板渲染失败转可读业务错误

### 6.2.3 Domain 层
只抛出明确的业务语义异常，不关心 HTTP 状态码。

### 6.2.4 Infrastructure 层
可以捕获底层异常并包装为统一基础设施异常。

## 6.3 统一异常处理目标

- 对前端与 Open API 返回标准化错误体
- 对内部记录完整异常上下文
- 自动带出 TraceId
- 根据异常类别选择合适日志级别
- 不向外暴露敏感技术细节

## 6.4 处理规则建议

| 异常类型 | HTTP | 日志级别 | 是否告警 |
|---|---|---|---|
| 参数校验异常 | 400 | Information / Warning | 否 |
| 认证异常 | 401 | Warning | 视频率 |
| 授权异常 | 403 | Warning | 视频率 |
| 资源不存在 | 404 | Information | 否 |
| 状态冲突 | 409 | Warning | 否 |
| 业务规则异常 | 422 | Information / Warning | 否 |
| 可重试依赖异常 | 500 / 503 | Error | 是 |
| 未知系统异常 | 500 | Error / Critical | 是 |

# 7. 业务异常设计

## 7.1 业务异常特点

业务异常具有以下特点：

- 预期内可能发生
- 用户可理解
- 可映射为稳定错误码
- 一般不需要系统级告警
- 必要时需要业务日志，不一定需要异常堆栈

## 7.2 典型业务异常场景

### 7.2.1 线程相关
- 当前线程状态不允许归档
- 当前线程未认领不可标记完成
- 已关闭线程不可继续转派

### 7.2.2 发件相关
- 发件任务已发送成功不可编辑
- 已取消任务不可直接发送
- 已超过最大重试次数

### 7.2.3 审批相关
- 当前用户不是审批人
- 审批单状态不是待审批
- 已撤回审批单不可审批

### 7.2.4 附件相关
- 附件不存在
- 附件不允许下载
- 敏感附件缺少额外授权

### 7.2.5 模板与规则相关
- 模板变量缺失
- 规则配置非法
- 禁用规则不可测试执行

## 7.3 业务异常编码建议

业务异常必须绑定稳定错误码，例如：

- `MAIL.THREAD.INVALID_STATUS`
- `MAIL.THREAD.CLAIM_FORBIDDEN`
- `MAIL.SENDTASK.RETRY_LIMIT_EXCEEDED`
- `MAIL.APPROVAL.NOT_CURRENT_APPROVER`
- `MAIL.ATTACHMENT.DOWNLOAD_FORBIDDEN`

## 7.4 业务异常消息建议

一类业务异常通常应有两层文本：

1. **对外 message**：简明、友好、稳定
2. **内部 details**：包含更多上下文用于排查

示例：

```text
message: 当前线程状态不允许归档
details: threadId=xxx, currentStatus=Processing, expected=Completed
```

# 8. 基础设施异常设计

## 8.1 基础设施异常特点

基础设施异常往往来源于：

- 数据库
- Redis
- SMTP / IMAP / POP3
- 对象存储
- 搜索引擎
- 第三方 HTTP 服务
- 文件转换 / 病毒扫描服务

其特点是：

- 常与环境或依赖状态有关
- 有些可重试，有些不可重试
- 必须记录原始异常上下文
- 常常需要运维关注和告警

## 8.2 典型异常场景

### 8.2.1 邮箱同步异常
- IMAP 登录失败
- 文件夹读取失败
- UID 同步中断
- 协议层超时

### 8.2.2 发件异常
- SMTP 鉴权失败
- SMTP 服务器拒绝
- TLS 协商失败
- 发件超时

### 8.2.3 存储异常
- 附件对象不存在
- 存储桶权限异常
- 预签名生成失败

### 8.2.4 数据持久化异常
- 唯一索引冲突
- 死锁
- 连接池耗尽
- 事务提交失败

## 8.3 基础设施异常处理建议

- 将底层组件异常包装为统一类型
- 明确区分“可重试”与“不可重试”
- 记录依赖名称、目标地址、资源 ID、超时时间
- 对高频失败触发告警
- 不直接把第三方原始错误透传给前端

# 9. 接口错误响应规范

## 9.1 标准错误响应结构

建议统一返回：

```json
{
  "code": "MAIL.THREAD.INVALID_STATUS",
  "message": "当前线程状态不允许归档",
  "details": "仅已完成线程允许归档",
  "validationErrors": [],
  "traceId": "00-6f4b8b8c4d8f6f3f4a1a...",
  "timestamp": "2026-04-26T08:30:00Z"
}
```

## 9.2 字段说明

| 字段 | 类型 | 说明 |
|---|---|---|
| `code` | string | 稳定业务错误码或系统错误码 |
| `message` | string | 面向调用方的错误说明 |
| `details` | string | 可选，补充说明 |
| `validationErrors` | array | 参数校验错误列表 |
| `traceId` | string | 追踪 ID |
| `timestamp` | string | 服务端时间 |

## 9.3 参数校验错误示例

```json
{
  "code": "COMMON.VALIDATION_ERROR",
  "message": "参数校验失败",
  "validationErrors": [
    {
      "field": "pageSize",
      "message": "pageSize 必须在 1 到 100 之间"
    },
    {
      "field": "mailAccountId",
      "message": "mailAccountId 不能为空"
    }
  ],
  "traceId": "00-xxxx",
  "timestamp": "2026-04-26T08:30:00Z"
}
```

## 9.4 未知异常响应原则

未知异常时：

- 返回统一系统错误码
- 不返回堆栈
- 不返回数据库/服务端内部实现信息
- 保留 traceId 供排查

示例：

```json
{
  "code": "COMMON.INTERNAL_ERROR",
  "message": "系统繁忙，请稍后重试",
  "traceId": "00-xxxx",
  "timestamp": "2026-04-26T08:30:00Z"
}
```

# 10. 日志设计总览

## 10.1 日志目标

系统日志要支撑四类核心目标：

1. **开发调试**：知道代码在哪一步失败
2. **运维排障**：定位环境、依赖、性能问题
3. **安全追踪**：识别越权、恶意调用、异常下载
4. **业务回溯**：知道某封邮件、某个线程、某次审批经历了什么

## 10.2 日志分类

建议至少划分以下日志类型：

- 应用运行日志
- 访问日志
- 业务操作日志
- 审计日志
- 集成调用日志
- 后台任务日志
- 安全事件日志

## 10.3 日志边界

### 适合写入普通应用日志的内容
- 请求进入与结束
- 参数摘要
- 关键分支结果
- 依赖调用成功/失败
- 性能耗时
- 异常堆栈

### 不适合写入普通应用日志的内容
- 完整邮件正文
- 明文凭据
- 大块附件元数据
- 全量请求体原文
- 敏感下载地址

# 11. 日志分级与输出策略

## 11.1 建议日志级别

| 级别 | 使用场景 |
|---|---|
| Trace | 超细粒度调试，仅开发或短期开启 |
| Debug | 调试信息、关键分支细节 |
| Information | 正常业务里程碑、关键动作完成 |
| Warning | 可预期异常、权限拒绝、重试、降级 |
| Error | 功能失败、依赖错误、未恢复异常 |
| Critical | 核心故障、安全事件、系统不可用 |

## 11.2 级别使用建议

### Trace / Debug
用于：

- 邮件归并决策细节
- 规则匹配过程
- 模板渲染变量展开
- 同步任务分页过程

生产环境默认不建议长期打开。

### Information
用于：

- 用户认领线程成功
- 发件任务创建成功
- 审批通过
- Webhook 投递成功
- 手工同步已触发

### Warning
用于：

- 当前用户无权限下载附件
- Webhook 第一次投递失败
- Open API 签名失败
- 线程认领冲突
- 幂等冲突

### Error
用于：

- SMTP 发件失败
- 数据库事务提交失败
- 附件下载代理失败
- 同步任务中断
- 对象存储不可达

### Critical
用于：

- 密钥解密失败
- 核心依赖全面不可用
- 审批逻辑出现绕过疑似
- 大量异常发件
- 日志系统写入故障影响核心链路

## 11.3 日志级别与告警关系

| 级别 | 默认告警 |
|---|---|
| Information | 否 |
| Warning | 仅高频或指定规则 |
| Error | 是 |
| Critical | 立即告警 |

# 15. 审计设计总览

## 15.1 审计的核心目标

审计的重点不是“记录所有东西”，而是确保关键问题能回答：

- 谁做了什么
- 对哪个资源做的
- 什么时候做的
- 为什么做的
- 结果如何
- 是否满足审批/授权要求
- 是否可复原关键过程

## 15.2 审计与普通日志的区别

| 维度 | 普通日志 | 审计日志 |
|---|---|---|
| 目的 | 调试、排障、监控 | 责任追踪、合规、安全 |
| 生命周期 | 可按运维策略滚动 | 通常保留更久 |
| 可修改性 | 可清理可归档 | 应尽量防篡改 |
| 内容重点 | 程序运行过程 | 用户行为与关键结果 |
| 查询方式 | 技术检索 | 业务与责任检索 |

## 15.3 审计类型

建议划分为：

- 业务审计
- 安全审计
- 配置审计
- 集成审计
- 访问审计

# 19. TraceId、CorrelationId 与可观测性设计

## 19.1 TraceId 的作用

TraceId 用于追踪一次技术调用链。
典型场景：

- 用户点击“发送”
- API 调用应用服务
- 应用服务调用审批判断
- 后台发件任务执行
- 记录日志与审计
- 推送 Webhook

这些环节应共享同一追踪链。

## 19.2 CorrelationId 的作用

CorrelationId 更偏业务关联，例如：

- 某次发件业务流程
- 某次审批流程
- 某次同步作业
- 某次 Open API 请求

一个业务过程可能跨多个 Trace。

## 19.3 使用建议

| 标识 | 用途 |
|---|---|
| `traceId` | 技术调用链跟踪 |
| `correlationId` | 业务流程关联 |
| `jobId` | 后台任务实例识别 |
| `eventId` | 事件/消息识别 |

## 19.4 传递规则建议

- 外部请求若带 `X-Correlation-Id`，系统可校验后透传
- 系统内部异步事件应携带 `traceId` 和 `correlationId`
- Webhook 推送日志应记录原始业务 `traceId`
- Open API 调用结果应可回查到原始请求链

# 20. 日志脱敏与隐私保护

## 20.1 必须脱敏的字段

以下字段不得以明文记录在普通日志中：

- 邮箱密码
- AccessToken / RefreshToken
- AppSecret
- Webhook Secret
- HTML 全文
- 敏感附件真实下载地址
- 用户个人隐私数据（视业务字段而定）

## 20.2 建议脱敏的字段

| 字段 | 脱敏建议 |
|---|---|
| 邮箱地址 | `a***@example.com` |
| 手机号 | 中间四位脱敏 |
| 身份证号 | 中间位脱敏 |
| 文件名 | 视场景部分脱敏 |
| 客户名称 | 部分脱敏或仅记录 ID |

## 20.3 请求体日志策略

对于写接口：

- 默认只记录摘要字段
- 不记录完整正文
- 对敏感字段用 `***`
- 对大对象只记录长度、数量、哈希摘要

示例：

```json
{
  "mailAccountId": "uuid",
  "recipientCount": 3,
  "bodyHtmlLength": 2048,
  "attachmentCount": 2
}
```

## 20.4 审计中的脱敏

审计日志虽然更正式，但也不应过度暴露敏感值。
例如：

- 记录“已轮换密钥”，而不记录新密钥值
- 记录“附件已下载”，而不记录可直接使用的下载链接

# 21. 存储、归档与保留策略

## 21.1 日志存储分层建议

建议按用途分层：

### 热数据
- 最近 7~30 天
- 用于快速排障和运营查询

### 温数据
- 最近 1~6 个月
- 用于回溯分析和审计查询

### 冷数据
- 长期归档
- 用于合规和历史追踪

## 21.2 保留周期建议

| 数据类型 | 建议保留周期 |
|---|---|
| 普通应用日志 | 30~90 天 |
| 错误日志 | 90~180 天 |
| Open API 调用日志 | 180 天 |
| Webhook 投递日志 | 180 天 |
| 同步任务日志 | 180 天 |
| 附件访问日志 | 365 天或以上 |
| 审计日志 | 按合规要求长期保留 |

## 21.3 归档要求

- 归档前可压缩
- 审计与安全日志优先独立归档
- 保持按时间、模块、事件类型可检索
- 关键日志建议不可被普通业务用户删除

## 21.4 清理策略

- 自动清理过期普通日志
- 安全日志、审计日志清理需审批或系统策略控制
- 清理动作自身也应审计

# 22. 告警与运维联动设计

## 22.1 告警目标

日志不是终点，告警才是让问题被真正看见的关键。
系统应把异常、错误日志和审计事件转化为可响应的告警。

## 22.2 重点告警场景

### 22.2.1 运行稳定性类
- SMTP 发件失败率持续升高
- IMAP 同步连续失败
- 数据库连接异常
- 对象存储不可达
- Webhook 大面积投递失败

### 22.2.2 安全风险类
- Open API 签名失败暴增
- 同一 IP 高频权限拒绝
- 同一附件短时间大量下载
- 大量审批拒绝或异常发送
- 大量敏感附件访问

### 22.2.3 业务异常类
- 发件任务积压
- 审批任务积压
- 同步任务长时间未完成
- 重试队列异常增长

## 22.3 告警级别建议

| 级别 | 场景 |
|---|---|
| P1 | 核心发件链路故障、审批绕过疑似、大面积服务不可用 |
| P2 | Open API 高频失败、Webhook 大面积失败、同步任务异常堆积 |
| P3 | 单模块错误率升高、普通限流触发、业务冲突异常升高 |

## 22.4 告警去噪建议

避免告警风暴：

- 聚合同类异常
- 设置最小触发阈值
- 设置告警静默窗口
- 区分业务异常与系统故障
- 使用错误率而非单次错误触发

# 23. 开发实施建议

## 23.1 编码规范建议

### 不建议
```csharp
catch (Exception ex)
{
    throw new Exception("失败");
}
```

### 建议
- 保留原始异常
- 转换为明确业务或基础设施异常
- 补充上下文信息
- 交给统一异常处理

## 23.2 日志编写规范

### 建议写法
- 消息模板固定
- 结构化参数独立传入
- 不做字符串拼接堆砌

### 不建议写法
```csharp
_logger.LogInformation("send task:" + task.Id + " success");
```

### 建议写法
```csharp
_logger.LogInformation("Send task succeeded. SendTaskId={SendTaskId}", task.Id);
```

## 23.3 异常抛出规范

- 参数错误用校验异常
- 权限问题用授权异常
- 状态非法用业务异常
- 外部依赖失败用基础设施或集成异常
- 不要滥用通用 `Exception`

## 23.4 关键节点必须记录日志

以下节点建议至少有一条日志：

- 请求进入与完成
- 关键业务动作开始与结束
- 外部依赖调用前后
- 状态机转换成功与失败
- 审批决策
- 发件执行结果

# 24. 测试与验收建议

## 24.1 异常处理测试

至少覆盖：

- 参数错误返回是否规范
- 业务异常错误码是否正确
- 未知异常是否隐藏内部细节
- traceId 是否返回
- 状态冲突是否返回 409/422

## 24.2 日志测试

至少覆盖：

- 关键动作是否落日志
- 日志是否带 traceId / resourceId
- Error 日志是否包含异常栈
- 请求体是否按策略脱敏
- 高并发时日志是否可关联

## 24.3 审计测试

至少覆盖：

- 审计事件是否完整记录操作人
- 审计是否记录关键资源 ID
- 失败操作是否记录
- 敏感操作是否可追溯
- 密钥轮换是否仅记录动作而不泄露值

## 24.4 安全与隐私测试

至少覆盖：

- 日志是否泄露明文密码
- 是否泄露 Token
- 附件下载地址是否被完整记录
- HTML 正文是否被完整打入普通日志
- 审计数据是否存在越权查看风险

# 26. 结论

邮件管理系统的异常处理、日志与审计设计，应围绕以下核心理念建立：

1. **异常必须具备业务语义和统一映射规则，不能靠零散 try-catch 拼接**
2. **日志必须结构化、可追踪、可检索，服务于调试、运维、安全和业务回溯**
3. **审计必须覆盖高风险配置、发件、审批、附件访问和开放接口操作**
4. **普通日志与审计日志必须分工明确，同时共同支撑问题定位与责任追踪**
5. **TraceId、CorrelationId、JobId、EventId 必须贯穿请求、异步任务与集成链路**
6. **敏感信息最小暴露是底线，日志有价值的前提是不泄密**
7. **错误响应、日志、审计、告警应组成完整闭环，而不是彼此孤立**

通过本方案，系统可以在面对业务异常、依赖故障、安全风险和运维排障时，具备稳定响应、快速定位、完整留痕和持续改进的能力。
