# 2. 总体设计原则

## 2.1 多租户原则
- `tenant_id` 表示租户/企业边界
- **不得**用 `tenant_id` 表示用户归属

## 2.2 用户维度建模原则
用户关系分为四层：
1. **租户层**：哪个公司
2. **邮箱归属与授权层**：谁能访问哪个邮箱
3. **邮件协同层**：谁负责、谁参与、谁审批
4. **用户态层**：某用户是否已读、星标、归档、隐藏

## 2.3 核心分层原则
- 邮件主数据与正文分离
- 邮件主数据与附件元数据分离
- 业务表与日志表尽量分离
- 用户个性化状态与全局状态分离

## 2.4 审计与扩展原则
- 核心业务表保留审计字段
- 可扩展对象建议保留 `extra_properties jsonb`
- 高增长日志表可不强制数据库级外键

# 3. 命名规范

## 3.1 表命名
统一使用 `snake_case` 复数形式，例如：
- `mail_accounts`
- `mail_messages`
- `mail_send_tasks`

## 3.2 字段命名
统一使用 `snake_case`，例如：
- `mail_account_id`
- `owner_user_id`
- `creation_time`

## 3.3 主键规范
- 字段统一：`id`
- 类型统一：`uuid`

## 3.4 审计字段规范
核心业务表建议统一包含：
- `tenant_id`
- `creation_time`
- `creator_id`
- `last_modification_time`
- `last_modifier_id`
- `is_deleted`
- `deleter_id`
- `deletion_time`

日志/快照/事件类表可视情况仅保留：
- `tenant_id`
- `creation_time`

# 16. 最终结论

本最终整合版数据库设计已经完整覆盖：

- 邮箱账号与归属授权
- 邮件线程、邮件正文、收件人、文件夹
- 共享邮箱用户态
- 协同分派、评论、审批、待办
- 附件管理
- 标签与分类
- 模板与签名
- 规则引擎
- 业务对象关联
- 收发任务
- 集成、幂等、Webhook、事件日志
- 审计与配置变更
- 日统计与处理统计

并且解决了之前最关键的问题：

1. `tenant_id` **只用于多租户，不用于用户区分**
2. 邮件权限不再简单依赖邮箱主表，而是通过**邮箱授权模型**实现
3. 用户态信息（已读、星标、隐藏、归档）从主表剥离，改由 `mail_user_message_states` 管理
4. 共享邮箱、个人邮箱、部门邮箱、系统邮箱都能在同一模型下稳定落地
5. 与 `ABP` 的用户、角色、组织单元和权限体系能自然衔接
